# Chronoscope — Product

> See [PRD.md](PRD.md), [ui-sketch.md](ui-sketch.md) and [theme-selector.md](theme-selector.md).

This is the living description of Chronoscope as built. The final docs task of every cycle folds that cycle's changes into it. Cycle specs (`cycle-N-SPEC.md`) describe changes against it, and [cycle-1-SPEC.md](cycle-1-SPEC.md) is the first one.

How the product is built and tested is in the project guidelines: [architecture.md](architecture.md), [coding.md](coding.md) and [testing.md](testing.md).

## 1. Overview

Chronoscope is a keyboard-first (mouse-capable), themeable terminal UI for browsing coding-agent sessions. You pick a harness, project and session in a selector overlay, then read the conversation as a stack of rounded blocks: user prompts, assistant text, thinking, and tool calls. Detail is hidden behind folds, so you can skim the high-level flow and unfold the parts you care about. Open sessions update live while the agent is still working.

v1 harnesses: **Claude Code** and **OpenCode**. The adapter interface is designed so that **Codex** and **Pi** can be added later without UI changes.

### 1.1 Events, focus and keys

How events reach components is in [architecture.md](architecture.md#events-focus-and-keys). What the user sees of it:

- Exactly one pane or overlay has focus at a time. A focused pane shows it with the `ring` border (§7.2).
- Opening an overlay or a prompt gives it focus. Closing it returns focus to whatever had it before.
- Global keys (quit, `?`, `t`, `Ctrl-o`) work everywhere, except while a prompt, the help overlay, the details overlay or the theme selector has focus. Those handle their own keys (input mode, §5; `Esc` / `?` closes help, `Esc` / `i` closes details). `Ctrl-c` always quits. In the selector, `t`, `?` and `q` still work (§5.6).
- The wheel and clicks act on the element under the pointer, whether or not it has focus (§5.9). While an overlay is open (selector, help, details, theme selector), nothing under it reacts to the mouse, and a click outside the overlay closes it.

## 2. Data sources (observed)

### 2.1 Claude Code

- Location: `~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl` (append-only JSONL).
- Directory name is a lossy encoding of the cwd (`/` and `.` → `-`); the real cwd is in each entry's `cwd` field.
- Subagent transcripts: `<session-uuid>/subagents/agent-<agentId>.jsonl` (entries have `isSidechain: true`) + `agent-<agentId>.meta.json` (`agentType`, `description`, `toolUseId`).
  - Linkage: the parent's `Agent` `tool_use.id` equals `meta.toolUseId`, and the matching `tool_result` entry's `toolUseResult.agentId` names the file.
  - **Subagent files read for tokens.** The session's token total (§4.1) reads the main transcript and every `agent-*.jsonl` found recursively below `<session file without extension>/subagents/`. Workflow runs nest theirs under `subagents/workflows/<run>/`. Other files there, such as `journal.jsonl` and the `.meta.json` files, are not transcripts and are not read. Links to directories (and a `subagents` directory that is itself a link) are not followed, and entries that are not regular files are left out. A missing `subagents` directory means no subagents. A file that cannot be read is logged and skipped, and the rest still count. Each message counts once per file, using its latest usage, keyed by message id (a message appeared in only one file in all 20 973 messages checked, so nothing is deduplicated across files).
- Relevant entry types: `user`, `assistant`, `system` (e.g. `turn_duration`), `attachment`, `ai-title`, `last-prompt`, `cost-state`.
  Noise to skip: `api-request*`, `mode`, `permission-mode`, `atis-latch`, `file-history-*`.
- Assistant entries carry `message.model`, `effort` / `perTurnEffort`, `timestamp`, `message.usage`, `message.stop_reason` and, for an API error, `isApiErrorMessage: true`.
  - Read from `usage`: `input_tokens`, `output_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens`, plus `output_tokens_details.thinking_tokens`, which is already part of `output_tokens`.
  - `stop_reason` is null on many lines of a message. The last non-null value per message id is the one that counts.
  - A message whose model is `<synthetic>` is generated by Claude Code itself (for example `No response requested.`).
- Content blocks: `text`, `thinking` (usually redacted — empty text + signature; ~15% of blocks observed carry readable text), `tool_use`, `server_tool_use`, `advisor_tool_result`; tool results arrive as `tool_result` blocks inside `user` entries, paired by `tool_use_id`.
- Session title available via `ai-title` (written repeatedly; use the **last** one).
- `system` `turn_duration` entries carry `timestamp` and `durationMs`. `messageCount` is a running total for the whole session, not a count for the turn (a 3-second turn reported 4124), so it is **not read**. One Assistant turn can contain many `turn_duration` entries, and `durationMs` restarts when a delivery such as a `queued_command` attachment with a non-human origin arrives.
- `toolUseResult` on a result entry is usually an object and sometimes a string, and can be very large (stdout, whole files). The assembler and the details overlay read it through an object-or-ignored head and never materialise it as a JSON value. The only field the assembler reads is `isAsync`: when `true`, the result records only the launch of an asynchronous subagent.
- **Detail fields are not parsed into the model.** Their availability varies across Claude Code versions and they are rarely looked at, so a turn keeps only the byte range of the line each section came from (§4.1), and the fields are read again when the details overlay opens (§3.3): `message.id`, `requestId`, `timestamp`, `requestedModel`, `stop_reason`, `usage.service_tier`, `speed` and `inference_geo`, `usage.cache_creation` (5-minute and 1-hour writes), `usage.server_tool_use` (web search and fetch counts) and `diagnostics.cache_miss_reason` on assistant lines; `permissionDecision`, `sandboxed`, `resolvedModel` and `isAsync` on the result of a tool call (at the top of the entry or inside `toolUseResult`); `permissionMode` and `promptSource` on prompts; `gitBranch`, `cwd`, `version` and `entrypoint` on every line. Claude records no cost.
- Every one of these fields is optional. The details overlay's re-read treats a field of an unexpected type as missing and only drops its row; what assembling does with a wrong type is in §8.5.
- **One JSONL line per content block:** an assistant API response is split over several `assistant` lines sharing `message.id` (BRIO session: 195 lines → 73 messages, up to 16 lines per message).
- **Most `user` entries are not human prompts:** in the BRIO session, 80 of 92 `user` entries only carry `tool_result` blocks. Human prompts have `origin.kind == "human"` and no `tool_result`. Entries with `isMeta: true` are injected, not typed.
- **Local commands.** A local command (`/effort`, `/model`, `/clear`, …) is handled by the harness and is not a prompt to the model. It is recorded as `user` entries, and it never starts a turn. A `user` entry is local-command content when all of these hold: it has no `origin` field; it is not `isMeta`, not a compact summary and holds no `tool_result`; and its text, with leading whitespace trimmed, starts with `<command-name>` (the echo), `<local-command-stdout>` or `<local-command-stderr>` (the output). The rule needs only the entry itself, so the transcript scan applies it line by line, with the same prompt rule as the assembler (§4.1). It was checked against 61 local sessions: all 45 local-command echoes have no `origin` and start with `<command-name>`, and all 30 echoes of commands that do reach the model (`/factory`, `/statusline`, `/doctor`) have `origin.kind` `human` and start with `<command-message>`, so they stay prompts. Not local commands: a prompt typed with a leading space, such as ` /clear` (sent to the model, recorded with `origin.kind` `human`, and a turn); `!` shell commands (`<bash-input>`, `<bash-stdout>`, `<bash-stderr>`), whose output reaches the model and which keep their rows; and OpenCode, which records no local commands. The `<local-command-caveat>` meta entry is an ordinary `isMeta` entry.

### 2.2 OpenCode

- Location: `~/.local/share/opencode/opencode.db` (SQLite, WAL mode).
- Tables: `project` (`worktree`, `name`), `session_v2` (`project_id`, `parent_id`, `directory`, `title`, `model`, tokens/cost, timestamps), `session_message` (`session_id`, `type`, `seq`, `data` JSON).
- Message types: `user`, `assistant`, `synthetic`, `system`, `idle`. Assistant `data` has `agent`, `model {id, providerID, variant}`, `time {created, streamed, completed}`, `cost`, `tokens {input, output, reasoning, cache {read, write}}`, `finish`, `rawFinish`, `error {type, message}`, and a `content` array of `text` / `tool` parts.
  - `tokens.reasoning` is separate from `tokens.output`; the adapter adds it to `output` (§4.1).
  - A row with `finish: "error"` has empty content. Its `error` is shown as a notice (§4.2).
  - A tool part's `time` (`created` and `completed`) gives the duration of the call.
  - The details overlay (§3.3) reads the row again when it opens: its id, `time.*`, `finish`, `rawFinish`, `error`, `model.providerID`, `agent`, a tool part's `time.created`, and `snapshot.start` and `snapshot.end`. A turn keeps only the id of the row (§4.1).
- Subagent sessions are linked via `session_v2.parent_id`.
- **Descendant rows read for tokens.** The session's token total (§4.1) sums the `tokens` of the `assistant` rows of the session and of every descendant session, following `parent_id` at any depth (only one level exists locally, but the rule is not limited to it), with `reasoning` added to `output` as the assembler does. Only rows the assembler parses count, so a row it skips for a wrong-typed field adds no tokens. The `session_v2.tokens_*` columns are not read: they differ from the row sums in 4 of 160 local sessions, and the rows are what the footers use.

## 3. Screens

### 3.1 Session selector overlay

Layout as in ui-sketch.md: harness tabs, Projects list, Sessions list, the Session Time and Session Tokens panels below it, Working Directory box, and help/search line.

Sizing:
- Width: the full terminal width, up to 160 columns; on wider terminals it is 160 columns wide and centred horizontally. Height: the terminal height minus one row above and one below.
- The Projects pane takes a third of the content width, but at least 20 and at most 36 columns. The Sessions pane gets the rest, so extra width mainly goes to the session list.
- The two panels (below) are stacked directly below the Sessions pane, `Session Time` first, with no gaps, and each is as wide as the Sessions pane. The bottom border of `Session Tokens` is on the same row as the Projects pane's. `Session Time` is 4 rows high (two borders and two text rows) and `Session Tokens` is 7 rows high (two borders and five text rows), 11 rows in total, with no blank rows. The Sessions pane loses those rows. Projects, the Working Directory box and the help line do not move.
- **Short terminals.** The panels are shown only when the Sessions pane keeps at least 3 list rows (a pane height of 6). That needs panes of 17 rows, so a terminal of at least 33 rows. Below that, neither panel is drawn and the Sessions pane has its full height. One panel is never drawn without the other.
- The list's visible rows, paging, scrolling and mouse hit area all follow its pane's height. The selected row stays visible when the terminal is resized and the panels appear or disappear.

Session row format: `<local start timestamp>  <title>` on the left, plus muted stats on the right (`<n> turns · <duration>`, `1 turn` for one). The model is not shown: the browser shows it on every Assistant turn.
- Title: Claude `ai-title` → OpenCode `session_v2.title` → first user prompt (truncated) → `(untitled)`. The first prompt is the first prompt of the browser's turns (§4.1), so a local command (§2.1) is never a session's first prompt: a session without an `ai-title` that began with `/effort` is titled from its next real prompt, and one with only local commands is `(untitled)`. Search over the first prompt follows.
- `<n>` is the number of User turns on Claude (§4.1) and the number of `user` rows on OpenCode, so it equals the number of `User` rows of the turns sidebar. `<duration>` is the session's **agent time** in the shared format below: the sum of the durations of the Assistant turns, summed exactly from the durations the sidebar shows (§4.1, rule 6), and only then formatted. Summing first matters, because the formatter truncates and adding the displayed values by hand can differ by up to a minute per turn from the total. A turn without a footer (one still running, or interrupted before its first `turn_duration`) shows no duration in the sidebar and adds nothing. Subagent time is not added, so that the row matches the sidebar. A session that holds only local commands has no turns to attach to, and its row reads `0 turns · 0s`.
- Stats are computed in the background and cached (§8.2). Until they are ready, the row shows just timestamp + title. The cache stores both durations in milliseconds, so the display format can change without invalidating it.
- The title gets the room the stats leave. When that would be less than 10 cells, the stats are dropped from the row.

**Duration format.** Durations use one format everywhere: the selector's rows and its Session Time panel, the stats footer (§4.2), the turns sidebar (§3.2), the details overlay (§3.3) and tool calls of a minute or longer (§4.2). One shared formatter (`src/duration.rs`) provides it, so no component has its own.

| Duration | Resolution | Examples |
|---|---|---|
| Under 1 minute | 1 second | `0s`, `45s` |
| 1 minute up to, but not including, 1 hour | 1 second | `1m 0s`, `4m 3s`, `59m 59s` |
| 1 hour or longer | 1 minute | `1h 0m`, `3h 4m`, `2h 45m`, `26h 30m`, `100h 30m` |

Numbers are not zero-padded. Values are truncated, not rounded: `59m 59.9s` shows `59m 59s`.

Projects:
- Claude: one project per distinct real `cwd`, read from the session entries (not the lossy directory name).
- OpenCode: from the `project` table (`name`, else the basename of `worktree`).
- Display name: basename of the cwd, unless an alias is configured (§7.5). Projects are sorted by most recent activity.
- Sessions are sorted newest first.

Startup (no arguments):
- Opens the selector.
- Preselects the harness and project whose cwd matches `$PWD` (or the nearest ancestor), falling back to the most recently active project (the first in the list).
- Focus is on the Projects pane and **no session is selected**: the Sessions pane lists the project's sessions without a `>` marker.

Session selection:
- Opening the selector over an open session (`Ctrl-o`) selects that session, with focus on Sessions.
- When the Sessions pane gets the focus (`Tab`, `Enter` on a project, `/`, clicking a row) and no session is selected, the newest session is selected.
- Moving to another project from the Projects pane (keys, click, wheel) clears the session selection again. Switching harness tab selects the first project, and its newest session only if Sessions has focus.
- While nothing is selected, live index updates keep the cursor on the newest session. `Esc` on a search that started from this state returns to it: Projects focused, no session selected.

Search (`/` in the selector):
- Fuzzy (`nucleo`) over title, first prompt and project name across **all projects of the current harness**.
- While a query is active, the Sessions pane shows matching sessions with their project name prefixed, and keeps the focus (`Tab`, `←`/`→`, `h`/`l` do nothing). `ESC` clears the query.

Each panel is a rounded block in `border`, titled as above, like the Working Directory box. Rows appear in this order, with the label left-aligned and the value right-aligned, one column inside each border.

`Session Time`:

| Label | Value | Format |
|---|---|---|
| `Total` | `run_time` | The shared duration format (above) |
| `Agent` | `agent_time` | The shared duration format; the same text as the row |

`Session Tokens`:

| Label | Value | Format |
|---|---|---|
| `Input` | `tokens.input` | `format_tokens` (§4.2), as in the details overlay |
| `Output` | `tokens.output` | `format_tokens` |
| `Thinking` | `tokens.reasoning` | `format_tokens` |
| `Cache read` | `tokens.cache_read` | `format_tokens` |
| `Cache write` | `tokens.cache_write` | `format_tokens` |

- The values are the session's `SessionStats` (§4.1). `Total` is the time from the session's first entry to its last (local commands count), idle time included, and `Agent` the time the agent was working. The tokens are the whole session's use, subagents included, so they are larger than the sum of the turn footers, which cover the main session only.
- Every label starts with a capital letter. The panel titles say what the values measure, so the labels do not repeat "time" or "tokens". Labels are muted and values are `foreground`.
- All rows of a panel always show together. A count no message reported is `0`.
- A row that cannot hold both keeps the value and cuts the label (with `…`, or leaves it out when nothing remains). Every label and value fits at the narrowest supported width (a 60-column terminal).

**When they show values.** Both panels show the selected session's stats, and both are an empty block (border and title, no rows) when:
- no session is selected (above), for example at startup, after moving to another project, or when a search has no results;
- the selected session's stats are not ready yet, or could not be computed.

Rules:
- The selected session is the one with the `>` marker, and while a search lists results the highlighted result. Selecting another session by any route (keys, mouse, wheel, search, `Ctrl-o`, switching harness) updates both panels in the same frame. They never show the previous session's values under a new selection. Opening the selector over an open session (`Ctrl-o`) shows that session's values on its first frame.
- When stats arrive for the selected session, the panels update without any key press. A running session's values follow its stats. Until a newer computation finishes, the last known values stay, as they do on the row.
- Stats for another session do not change the panels.
- The panels never take focus and are not in the `Tab` order. Clicks and wheel events over them do nothing, and do not reach the session list.
- Each panel is a component of its own (`SessionTime` with `Id::SessionTime`, `SessionTokens` with `Id::SessionTokens`, [architecture.md](architecture.md#components)), mounted and unmounted with the selector. The `App` pushes their values, as it does for the Working Directory box. Both join the themed components, so they follow a theme change.
- Drawing does no I/O or parsing: the panels show stats the worker already delivered.

### 3.2 Session browser

- Header block: `Project <name>` (left title), session id (right title), working directory in the body. A `● live` marker shows while the session is active (§6.2), and a breadcrumb shows when viewing a subagent (§4.4).
- Turns sidebar: a fixed pane to the left of the transcript that lists the session's turns (see below).
- Transcript: one rounded block per turn (§4.2), scrolling vertically, with the selected section marked by `▒` over the block's left border.
- Help line under the transcript and the sidebar, full width: context-sensitive key hints. It turns into the search/path prompt when active and shows search position (`3/17`), the `↓ N new` indicator and parse warnings.
- Toasts (copy/save/export confirmations, config warnings) appear in the bottom-right corner for ~2 s.
- Loading state: `Loading… 34%` in the help line while the initial parse streams in.
- Empty states: "No sessions for this harness" / "Session file is empty". A session that holds only local commands (§2.1) has no turns to attach them to and must not claim to be empty: the message is then **`No turns. Local commands only:`** followed by the commands, one per line, in the order they ran, as `/command args`. The message is centred as a block in the same place as the single line, each line on its own, and a line too wide for the area ends in `…`. A file with truly nothing in it still shows `Session file is empty`, and so does one with outputs but no command.
  - The commands come from the loader (`ModelUpdate::LocalCommands`, the whole list each time, sent only while the session has no turns and only when the list changed). They are the command of each echo; Claude Code writes a `system` `local_command` entry beside most echoes, so those entries are listed (by their command) only when the session has no echo at all. Outputs and the caveat are not commands. An echo with stray text is listed by its `<command-name>` alone, and tabs in the arguments show as spaces, so a list row is always one line.
  - The list belongs to its load: a reload, a reset or opening another session starts over. When a turn arrives in a live session, the browser replaces the state with the normal view, and the commands are part of the first User turn. Held entries after a trailing compaction (§4.6) keep their behaviour: they appear once a later turn arrives.

#### Turns sidebar

A sidebar lists the session's turns and compaction events, so the shape of a long session is visible and any block is a few keys away.

```
╭─ [1] Turns  ───────────────╮
│                            │
│  ┬   Start                 │
│  │                         │
│  ├   User                  │
│  │                         │
│  ├   Assistant      4m 3s  │
│  │                         │
│  ├   User                  │
│  │                         │
│  ├   Assistant      3h 4m  │
│  │                         │
│  ├╶╶ Compaction ╶╶╶╶╶╶╶╶╶  │
│  │                         │
│  ├   Assistant     2h 45m  │
│  │                         │
│  ┴   End                   │
│                            │
│                            │
╰────────────────────────────╯
```

**Layout.**
- The pane's title shows the key that focuses it (`[1] Turns` by default; it follows a remapped `focus_turns`).
- The `TurnSidebar` component ([architecture.md](architecture.md#components)) sits to the left of the transcript, below the header. Header and help line stay full width.
- It is **30 columns wide, with a 1-column gap** before the transcript, and exactly as tall as the transcript area. The gap belongs to a `SidebarGap` component that only paints the background.
- **It stays in a fixed position:** scrolling the transcript never moves the pane. Only its own list scrolls, and only as far as needed to keep the selected row visible, as in the selector's lists.
- The areas come from the pure layout function (§1.1), so drawing and mouse routing agree. The transcript's viewport and its mouse coordinates use the narrower area.
- **Below 90 columns the sidebar is hidden** and the transcript takes the full width, because 90 columns leave the transcript 59. While it is hidden the focus keys do nothing, and if it has focus when it becomes hidden, focus moves to the transcript.
- It is not drawn when the empty-session message replaces the transcript. An open subagent (§4.4) shows that subagent's turns, and going back shows the parent's again.

**Rows.** There is one entry per turn with at least one non-system section, in transcript order, decided by the same section derivation as the blocks `]` / `[` stop on. System content never forms a block of its own (§4.6), so toggling it (`s`) does not change the entries. Building the entries lays out and renders nothing.

| Row | Content | Selectable |
|---|---|---|
| `┬ Start` | First row of the list | No: it has no block |
| `├ User` | A User turn | Yes |
| `├ Assistant` | An Assistant turn, with its duration | Yes |
| `├╶╶ Compaction ╶╶╶` | A Compaction turn; `╶` fills to the right margin | Yes |
| `┴ End` | Last row of the list | No: it has no block |

- Columns (from 0): `┬`, `├`, `┴` and the selection marker in column 3; labels in column 7, with the Compaction rule running from column 4; the right margin is two cells before the border, as in the selector. One blank row separates the list from the top border.
- Between two rows of the list there is one row with `│` in column 3, so the timeline runs unbroken through a Compaction too. Connector rows cannot be selected or clicked.
- An Assistant entry shows the turn's duration (§4.2) in the shared format (above), right-aligned to the right margin. A turn without stats (for example, one still running) shows none, and it appears in place once known.
- Long lists scroll by rows; `Start` and `End` scroll with the list. The list never wraps around.
- Unselected rows, `┬`, `├`, `┴`, `│` and `╶` use `muted_foreground`.

**Selection** looks and behaves like the selector's lists (§7.2), except that its marker is `▒`: the border is `ring` when the sidebar has focus and `border` otherwise; the selected row in a focused sidebar has `▒` in `primary` in place of the `├` and one inverted band after it up to the right margin; in an unfocused sidebar the `▒` and the text are `secondary_foreground`, the text bold.

- **While the transcript has focus, the sidebar's selection follows it:** the selected row is the turn containing the transcript's selected section, and it stays visible. The sidebar shows the current position, and returning to it never jumps. Pushing that selection to the sidebar produces no message.
- When the sidebar has focus and nothing is selected, the first move selects the first entry. An empty list has no selection, and its keys do nothing.
- A live update adds or changes only the rows of the turns it names (§6.2): an appended turn adds a row without moving the selection.

**Performance.** The sidebar keeps one slot per turn and derives only the sections of a turn when it changes, never a layout or a render, and it draws only the rows it shows. A key press in the sidebar (selection, transcript scroll and frame) stays within the frame budget on the 100 MB fixture (§8.2).

### 3.3 Overlays

- **Help overlay** (`?`): grouped keybindings as in ui-sketch.md, generated from the active keymap. `Esc` / `?` closes it.
- **Details overlay** (`i`, the `details` action of `[keys.browser]`, listed as "Show section details" in the help overlay's Sections group): the metadata of the selected section, so that blocks stay uncluttered. See below.
- **Theme selector** (`t`): see §7.4.
- **Confirmation prompts** (overwrite file, resume in harness) appear in the help line as `y/n` questions, not as dialogs.

Overlays are centred, use rounded borders with `ring` colour, and paint `surface` behind them (unless the background is transparent, in which case `Clear` is still used so underlying text doesn't bleed through).

#### Details overlay

A `Details` overlay in the help overlay's frame: it reuses its sizing (as wide as its widest row, at most the screen less two columns either side), its scrolling and its keys (`↑↓` / `j` `k` a row, `PgUp` / `PgDn` a page, a `↓ more` hint when it is taller than the screen). `Esc` or the `details` key closes it, and focus returns to who had it.

- It opens for the selected section. A `… N more lines` row resolves to its parent tool call. With no selection, or while another overlay or a prompt is open, the key does nothing.
- It is a snapshot taken when it opens and does not update while open. It is not part of copy, save or export.
- Rows are `label  value`: labels in `muted_foreground`, values in `foreground`, under bold group headings. Groups that do not apply to the section, and rows whose field is missing, are left out.
- Timestamps use the configured format (§7.6). Durations use the shared format (§3.1) and token counts the footer's format (§4.2). Claude records no cost, so none is shown for it.

| Group | Applies to | Claude | OpenCode |
|---|---|---|---|
| Turn | Every section of an Assistant turn | `model`, `effort`, `start`, `duration`, `messages`, `input tokens`, `output tokens`, `thinking tokens`, `cache read tokens`, `cache write tokens` | The same, plus `cost`, `provider` (`model.providerID`) and `agent` |
| Message | Text, thinking, notice | `message.id`, `requestId`, `timestamp`, `requestedModel`, `stop_reason`, `service_tier`, `speed`, `inference_geo`, `5m cache writes`, `1h cache writes`, `web searches`, `web fetches`, `diagnostics.cache_miss_reason` | `row id`, `time.created`, `time.streamed`, `time.completed`, `finish`, `rawFinish`, `error` |
| Tool call | Tool call | `start`, `duration`, `status`, `permissionDecision`, `sandboxed`, `resolvedModel`, `isAsync` | `start`, `duration`, `status` |
| Prompt | User prompt | `timestamp`, `permissionMode`, `promptSource` | `time.created` |
| Environment | Every section with a source; compaction and system sections show their timestamp | `gitBranch`, `cwd`, `version`, `entrypoint` | `snapshot.start`, `snapshot.end` |

Groups come in this order. A token row of zero is left out, because the model cannot tell zero from not recorded.

**Where the rows come from.** The model supplies the rows it already holds (the Turn group, a tool call's `duration` and `status`, the timestamp of a prompt, a compaction or an injected entry). The rest is read from the section's source when the overlay opens (§4.1): the open session's harness adapter implements `section_details` ([architecture.md](architecture.md#data-flow)), re-reading one line (Claude: a byte range in the transcript, two for a tool call, its call and its result) or one row (OpenCode: the `session_message` row, through the read-only connection). The overlay's content is composed from both, so the UI stays harness-agnostic. A harness that provides nothing (Codex, Pi) leaves the model's rows alone.

An unreadable source (the file is gone, the row was deleted, the line does not parse) shows one muted `unavailable` row in the affected group, with what could be read before it. It never panics and never closes the overlay.

## 4. Conversation model & rendering

### 4.1 Normalised model

Harness adapters translate each native format into one shared model:

```
Session { id, harness, project, cwd, title, started_at, turns: [Turn], children: [SessionRef] }
Turn    = User      { timestamp, text, items: [Item], sources }     // items: injected content preceding/attached to the prompt
        | Assistant { timestamp, model, effort?, items: [Item], stats?: TurnStats, sources }
        | Compaction{ timestamp, summary, sources }
Item    = Text(markdown)
        | Injected { entries: [{ kind, timestamp, text }] }   // §4.6; consecutive entries collapsed
        | Thinking(text | Redacted)
        | ToolCall { id, tool: ToolKind, description, input, result?: ToolResult, status, duration? }
        | ModelChange { model }                                // the muted note of rule 5
        | Notice { id, level: Error | Warning, text }          // an abnormal ending, see below
ToolKind = Shell | Read | Write | Edit | Grep | Glob | WebFetch | WebSearch | Subagent | Other(name)
TurnStats  = { duration, message_count, tokens?: TokenUsage, cost? }
TokenUsage = { input, output, cache_read, cache_write, reasoning }
SessionStats = { turns, agent_time, run_time, tokens: TokenUsage }   // §3.1: the selector's row and panels
```

- **Tokens.** `TurnStats.tokens` is a `TokenUsage` summed over the turn's messages. Each message counts once, using its latest usage. `output` includes `reasoning` on every harness, and `reasoning` is only an "of which" figure that is never added to a total. The footer's `tokens` is input + output + cache writes (§4.2), and its `cached` is the sum of cache reads.
- **Session stats.** `SessionStats` is what the selector shows for a session without opening it (§3.1). It is computed in the background from the transcript or the rows, and cached (§8.2). A duration is stored in milliseconds, and `tokens` has the footer's `TokenUsage` shape.

  | Field | Claude | OpenCode |
  |---|---|---|
  | `turns` | The number of User turns (rule 1 below) | The number of `user` rows |
  | `agent_time` | The sum of the Assistant turns' `TurnStats.duration` (rule 6), a turn without a footer adding nothing | The same sum, from the OpenCode assembler's turns |
  | `run_time` | The last entry's timestamp minus the first's. Local-command entries count | `time_updated` minus `time_created` |
  | `tokens` | The whole session's use, below | The whole session's use, below |

  `tokens` is the session's whole use: the main session and all its subagents. `output` includes `reasoning`, and `reasoning` is never added to a total. It deliberately differs from the sum of the session's turn footers, which cover only the main session. Claude: the main transcript and the subagent transcripts of §2.1, each message counted once per file with its latest usage, keyed by message id. `TurnStats.tokens` is **not** summed, because it exists only once a turn has a footer, and a turn without one would be lost (12 of 250 Assistant turns locally, about 2% of the output tokens). A pass lighter than the `Assembler` is allowed over subagent files, as long as the result is the same. OpenCode: the `assistant` rows of the session and of its descendants (§2.2). Total time (`run_time`) and the turn count stay those of the main session on both harnesses.
- **Sources.** Every turn carries `sources`, a side table of cheap references to where its sections were read from, and never the field values (§2.1, §2.2): for Claude a `ByteSource` and a byte range per line (the prompt, the last `turn_duration` line, the latest line of each message with a non-null `stop_reason`, else its latest line, and for a tool call two ranges, its call and its result), for OpenCode the ids of rows. Items carry nothing of it. Adding to the table takes constant time per item and it is never searched while assembling, because one turn can hold tens of thousands of items. The details overlay (§3.3) reads through the references when it opens, so assembling a turn never parses the detail fields.
- **Durations.** `ToolCall.duration` is the time between the call and its result. It is empty for a pending call, when the adapter does not know it, and for an asynchronous subagent (Claude `toolUseResult.isAsync` is `true`), whose result only records the launch.
- **Notices.** An `Item::Notice` records how a message ended abnormally, because the turn would otherwise show nothing about it. Its id is `notice:<message or row id>` and it is upserted, so a row updated in place replaces its notice instead of adding another. A normal ending never produces one.

  | Harness | Input | Result |
  |---|---|---|
  | OpenCode | `finish: "error"`, `error.type` is `aborted` | `Warning`: `aborted`, followed by `: <error.message>` when there is one |
  | OpenCode | `finish: "error"`, any other type | `Error`: `<error.type>: <error.message>`, using whichever parts exist |
  | OpenCode | `finish` other than `stop`, `tool-calls`, `error` (absent is normal) | `Warning`: `stopped: <finish>` |
  | Claude | `isApiErrorMessage: true` | `Error` with the message's text, **replacing** its text block so it is not shown twice |
  | Claude | `stop_reason` other than `end_turn`, `tool_use`, `stop_sequence`, `pause_turn` | `Warning`: `stopped: <reason>` |

  A null Claude `stop_reason` alone produces no notice, and synthetic messages without `isApiErrorMessage` (such as `No response requested.`) stay ordinary text.

Turn assembly (Claude):
1. A **User turn** starts at a `user` entry that is a human prompt: `origin.kind == "human"` (or, for older versions without `origin`, string/text content with no `tool_result` and no `isMeta`), and that is not local-command content (§2.1; rule 7). A message typed while the agent is working is stored as an `attachment` of kind `queued_command` with `origin.kind == "human"`; it also starts a User turn, and the content after it forms a new Assistant turn.
2. Everything up to the next human prompt forms **one Assistant turn**: `assistant` lines, `tool_result`-only `user` lines, and allowlisted injected content (§4.6).
3. `assistant` lines with the same `message.id` are merged into one message, keeping their content blocks in order. Repeated blocks (same `tool_use.id`, or same index for text/thinking) replace the earlier version instead of being duplicated.
4. `tool_result` blocks are attached to the `ToolCall` with the matching `tool_use_id`. A tool call without a result yet has status `pending`.
5. The model shown in the Assistant title is that of the turn's first message. If the model changes within a turn, the new model is shown as a muted inline note.
6. `system` `turn_duration` entries become the stats footer of the preceding Assistant turn. A turn has a footer only once such an entry exists. The footer is built as follows:
   - **Duration:** wall-clock. It is the timestamp of the turn's last `turn_duration` entry minus the timestamp of the prompt that started the turn; for a turn without a prompt (for example, one following a compaction), minus the timestamp of its first assistant entry. Without a usable timestamp (or when the span would be negative), the last entry's own `durationMs` is used. Entries are never summed, because a turn can contain many of them and they restart on deliveries such as non-human `queued_command` attachments. The duration includes any time spent waiting on background agents.
   - **Messages:** the number of distinct message ids in the turn, leaving out messages whose model is `<synthetic>`. It stays current when messages arrive after a `turn_duration` entry. `messageCount` is a running total for the session and is not read.
   - **Tokens:** from each message's `usage`, per the tokens rule above. Claude's `thinking_tokens` is already part of `output_tokens`, so it only fills `reasoning`.
   - No cost: Claude records none, and there is no price table.
7. **Local commands** (§2.1) are neither prompts nor turns. Each echo and each output becomes an injected entry of kind `local_command` through the held-entries path of §4.6, the kind that `system` `local_command` entries already use. Like the other injected entries it joins the neighbouring block: into the next User turn when one follows, else into the current turn at the end of the input.
   - Its text drops the markup. An echo becomes the command and its arguments (`/effort`, `/model opus`), and an output becomes the text inside the tags (`Cancelled`). A body that does not match these forms exactly, such as an echo with stray text around its tags, is kept as it is.
   - The echo and its output are separate entries and are not merged.
   - A local command does not end the current Assistant turn: Assistant entries after it continue that turn, as they do when no local command came between them. It does not move the start of the turn's duration (rule 6), which stays the prompt's timestamp. It adds no turn, so the sidebar gains no row and the turn count (§3.1) does not change.
   - A live batch can end between a local command and the next prompt. As for every other injected entry, `flush_held` then places the entry in the current turn, and it stays there. Reloading the session places it in the next turn. Only the block holding the entry differs: the turns themselves do not.
   - A session that holds nothing else has no turn to hold the entries; the browser shows them as its empty state (§3.2).

Turn assembly (OpenCode): each `user` row (with `synthetic` rows treated as injected content) starts a turn. `assistant` rows up to the next `user` row form the Assistant turn. Tool calls and their results are already combined in each `tool` part (`state.input`, `state.content`, `state.status`). The stats come from the rows: the duration, the message count (assistant messages) and the cost, and the tokens from each row's `tokens` (`input`, `output` plus `reasoning`, `cache.read`, `cache.write`). A row with an abnormal `finish` produces a notice (table above).

- Tool names are mapped to `ToolKind` per harness (e.g. Claude `Bash` and OpenCode `shell` → `Shell`; Claude `Agent`/`Task` and OpenCode `subagent` → `Subagent`).
- Tool description: the tool's own `description` input if present (Claude Bash). Otherwise a derived label (`Read src/main.rs`, `Grep "pattern" in path`, `WebFetch example.com/…`, `<tool name>` for unknown tools).
- `effort` is shown only when the harness records it (Claude `effort`; OpenCode `model.variant` when it isn't `default`).

### 4.2 Blocks and sections

Each turn is rendered as a rounded block. Its title shows the role on the left and the timestamp on the right. Assistant blocks also show `model @ effort` after the role. A **section** is the unit of selection, folding, copying and saving.

| Section | Default fold | Folded shows | Unfolded shows |
|---|---|---|---|
| User prompt | Folded | First 2 lines + `…` | Full prompt |
| Assistant text | Not foldable | n/a | Rendered markdown |
| Thinking (readable) | Folded | `Thinking` + first line, muted | Full text, muted |
| Thinking (redacted) | Not shown | n/a | n/a |
| Tool call | Folded | `> <description>`, then the duration of a finished call (below) | Description and duration, then per-tool body (§4.3) |
| Subagent call | Folded | `> <description>` + agent name, then the duration, then a rule and the "open transcript" hint (title row, below) | The same title row, then prompt + final result |
| Notice | Not foldable | n/a | The text of an abnormal ending, word-wrapped (below) |
| Turn stats footer | Not foldable | One muted line: duration · messages · tokens · cached · cost (the parts that are known) | n/a |
| Compaction marker | Folded | Divider `── context compacted ──` | Summary text |
| System / injected | Folded | Muted one-liner: kind + first line | Full content, muted |

Redacted thinking (no readable text) is kept in the model (§4.1) but is not a section. It is not drawn, selected, searched, copied or exported, because it has nothing to show. A turn whose only content is redacted thinking is drawn as an empty block.

The folded/unfolded marker prefix is `▶` when folded and `▼` when unfolded (the sketch uses `>` and `-`).

Every section's text starts at the same column, two cells in from the block's padding:
- Foldable sections put their marker (`▶`/`▼` and a space) in those two cells.
- All other non-foldable lines (assistant text, `model → …` notes, notices, the turn stats footer) are indented by two spaces.

**Turn stats footer.** One muted line of the parts that are known, joined by ` · `:

```
5m 2s · 12 messages · 45.2k tokens · 359.4M cached · $0.42
```

- `5m 2s` is the turn's duration in the shared format (§3.1). `12 messages` is the message count (`1 message`).
- `45.2k tokens` is input + output + cache writes. Counts below 1 000 are plain (`950`), then `45.2k`, `1.2M`. Reasoning is already part of output and is not added.
- `359.4M cached` is the cache reads summed over the turn's messages. It is hidden when zero. It is shown apart from `tokens` because a session's cache reads are usually far larger than everything else.
- The cost, when known, stays last (`$0.42`). Claude records none.
- On a narrow block the line wraps between parts; a row never starts with the separator.
- Search matches the footer as displayed.

**Tool call rows.** A finished tool call shows a muted ` · 1.2s` after its description, and after the agent type of a subagent call (`(story-writer)`), both folded and unfolded. A pending call, a call whose duration is not known and an asynchronous subagent show none. When a folded row is too narrow, the description is cut with `…` first, and the agent type and duration are kept. Unfolded, the description is word-wrapped with the duration as its last, muted, words. Under a minute the duration has finer resolution than the shared format (§3.1), which would show most calls as `0s`:

| Duration | Shown as |
|---|---|
| Under 1 second | `340ms` |
| Under 60 seconds | `1.2s` |
| Otherwise | The shared format (§3.1): `5m 2s`, `1h 5m` |

Values are truncated, as in the shared format. The text that is copied, saved, exported and searched is the text displayed, so search highlights stay aligned with the cells drawn.

**Subagent title rows.** The title row of a subagent call is its folded row, or the last of the rows its description and duration are word-wrapped into when it is unfolded. It carries, after the description, a rule and the hint that opens the subagent's transcript (§4.4). This applies to every subagent call, folded or unfolded, selected or not, on both harnesses and in an opened subagent's transcript. From left to right the row holds the description, ` (<agent>)` and ` · <duration>` exactly as above, a gap of 2 cells, a rule of `─`, a gap of 2 cells and the hint `<key> to open transcript`, where `<key>` is the label of the `open_subagent` key (`a` by default, `Ctrl-o` or another label when remapped). The hint is right-aligned with one blank cell between it and the block's right border, the same gap as between the left border and the fold marker. The text area (the block's width `W` less 8) leaves 3 cells of padding before the right border, and a title row reaches 2 cells into it: it ends at column `W − 3` (counting from 0), column `W − 2` is blank and the border is at column `W − 1`. Only the rule and the hint go into the padding, and only on title rows: the description, the agent type and the duration still end within the text area. The rule fills every cell between the two gaps. Widths are display cells, not characters.

```
│ ▶ Explore the UVC descriptors (Explore)  ─────────────────────────────────  a to open transcript │
```

The rule and the hint use only the room the description leaves, and never cut, wrap or move the description, the agent type or the duration. Let `d` be the width of the description, agent type and duration on the title row, `h` the width of the hint, `t` the width of the text area (`W − 8`) and `r = t + 2` the width of the title row, from the text column to the cell before the right border's gap. The rule is at least 3 cells wide:

| Room | Title row |
|---|---|
| `d + 7 + h ≤ r` | Description, gap, rule, gap and hint. The rule is `r − d − 4 − h` cells, so it shrinks first, down to 3 cells |
| `d + 5 ≤ r < d + 7 + h` | The hint is left out. The gap and the rule run to the row's end, one cell before the border: the rule is `r − d − 2` cells |
| `r < d + 5` | Neither rule nor hint. The row is as without them, including a description cut with `…` |

A folded row whose hint is left out shows it nowhere else. An unfolded subagent always shows the hint. Its `d` is the width of the last description row only: the end of the description with the duration when it ends there, or the duration alone when it is on a row of its own. When the hint fits there (the first row of the table), the rule and the hint go on that row. Otherwise the hint goes on a row of its own directly below the description, and the description's rows have no rule. That row starts at the text column and is `r` cells wide: the rule runs from the text column to the gap before the hint, and the hint ends one cell before the right border. When `r < h + 5` the row holds only the hint, from the text column, cut with `…` when it is wider than `r`. The hint's own row belongs to the description rows and is followed by the blank row that follows the description. An unfolded subagent shows `Prompt:` and `Result:` and nothing after the result; the `… N more lines` row of a truncated result follows the result directly, as for every other tool call.

No background colour is painted. The rule is drawn in `border` (§7.2), whatever the selection and `dim_unselected`: it is never dimmed and never bold. The hint is `muted_foreground` and takes the section's emphasis, bold when the section is selected. The description, the agent type and the duration keep their styles. The rule and the hint are chrome, like the fold marker, and not the section's text: search matches the description row as drawn without them (`open transcript` is not a match), highlights are never drawn on them, and copy and save as displayed give the description rows without them (§5.4).

**Notice rows.** A `Notice` item (§4.1) is a section of its own kind in the turn's order. It is not foldable and is selectable. Its text is word-wrapped and indented like the other non-foldable lines. An `Error` is drawn in `error_output` and a `Warning` in `muted_foreground`. It is included in search, copy, save and export like the `model → …` note. When saved, the file-name word is `error` for an `Error` and `notice` for a `Warning` (§5.4).

### 4.3 Per-tool renderers

| ToolKind | Unfolded body |
|---|---|
| Shell | `Command:` (char-wrapped) + `Result:` (char-wrapped, error output in `error_output`) |
| Read | Path + line range, then file content with line numbers |
| Write | Path, then content (syntax-highlighted by extension) |
| Edit | Path, then a unified diff of old → new (`similar`), with added/removed lines coloured |
| Grep / Glob | Pattern (+ path / filters), then matches |
| WebFetch / WebSearch | URL or query, then result |
| Other (incl. MCP) | Pretty-printed input JSON + result text |

Results longer than N lines (default 200, configurable) are truncated, with a `… 1 234 more lines` row; pressing `Enter` on that row expands the rest.

### 4.4 Subagents

- Subagent sections show the prompt and the final result inline.
- The hint that names the key to open the transcript (`a to open transcript`) is on the section's title row, folded or unfolded, with a rule (§4.2), not in the body.
- A key (§5) opens the subagent's own transcript as a full session view: Claude `subagents/agent-<id>.jsonl`, OpenCode child `session_v2` via `parent_id`.
- The browser header shows a breadcrumb (`Project BRIO › Agent: story-writer`). A back key returns to the parent view at the same scroll position.

### 4.5 Text rendering

- Assistant text, user prompts and thinking are rendered as markdown (`pulldown-cmark`): headings, emphasis, lists, inline code, block quotes, tables, and fenced code blocks with syntax highlighting (`syntect`, mapped to theme colours).
- Prose is word-wrapped. Commands and tool output are char-wrapped (as in the sketch) so paths and long tokens are never hidden.
- Wrapping is recomputed when the terminal is resized.

### 4.6 Visibility toggles

- System/injected content is shown by default (muted, folded). A toggle key hides or shows all of it; the default is configurable (`show_system = true`).
- It is rendered as **System sections inside the adjacent turn**: in the next turn when it precedes a prompt, in the current turn otherwise. Consecutive injected entries collapse into one section with a count (`3 injected items`). They never become turn blocks of their own, so `[` / `]` only stop at User, Assistant and Compaction blocks.
- **Allowlist** of Claude content that counts as system/injected:
  - attachments `hook_system_message`, `file`, `directory`, `opened_file_in_ide`, `selected_lines_in_ide`, `queued_command` (except human messages, see §4.1), `instructions`, `plan_mode`, `plan_mode_exit`, `compact_file_reference`;
  - `system` entries with subtype `local_command`, `informational` or `away_summary`;
  - `user` entries with `isMeta: true`;
  - `user` entries that are local-command content (§2.1), which become `local_command` entries with the markup dropped (§4.1, rule 7).
- OpenCode: `synthetic` and `system` rows.
- **Everything else is noise and never shown:**
  - API request records, mode/permission changes, file-history snapshots, title / last-prompt / cost records;
  - all other attachment kinds (`total_tokens_reminder`, `deferred_tools_*`, `skill_listing`, `credential_org`, `batching_reminder_sent`, `environment`, `date`, `model`, `auto_mode`, …).
  - Unknown attachment kinds are treated as noise, but are counted in the log so the allowlist can be extended.

## 5. Interaction & keybindings

All keybindings are remappable in config (§7.5). The defaults avoid modifier+Enter combinations, which most terminals cannot distinguish from Enter.

**Input mode:** while a help-line prompt is active (search, file path, y/n confirmation), the `Prompt` component has focus (§1.1) and every printable key goes into the prompt. Only `Enter`, `Esc`, `Backspace`, the arrow keys and `Ctrl-c` keep their meaning there. This prevents conflicts such as `j` / `t` / `1`–`4` while typing a search.

### 5.1 Folding (session browser)

| Key | Action |
|---|---|
| `Enter` / `Space` | Toggle fold of current section |
| `←` / `h` | Fold current section |
| `→` / `l` | Unfold current section |
| `-` | Fold all |
| `+` / `=` | Unfold all |

Fold levels (`1`/`2`/`3`) and Vim-style `z` aliases (`za`, `zc`, `zo`, `zM`, `zR`) were considered and rejected. No default binding is a chord.

### 5.2 Transcript search

- `/` opens a query in the help line. Matching is smart-case substring (case-insensitive unless the query contains an uppercase letter).
- Searches **all** text, including folded sections, tool input/output and system content.
- `Enter` confirms and jumps to the first match; `n` / `N` go to the next / previous match. All matches are highlighted with `search_match`, and the help line shows `3/17`.
- Jumping to a match inside a folded section unfolds it temporarily. It refolds when the selection moves to a different section, unless the user unfolded it explicitly in the meantime.
- `ESC` clears the search and highlights.

### 5.3 Navigation (session browser)

| Key | Action |
|---|---|
| `↓` / `j`, `↑` / `k` | Select next / previous section |
| `]` / `[` | Jump to next / previous turn block (User / Assistant / Compaction) |
| `Ctrl-d` / `Ctrl-u` | Scroll half a page down / up |
| `PgDn` / `PgUp` | Scroll a full page down / up |
| `g` / `Home`, `G` / `End` | Jump to start / end (`G` resumes following, §6.2) |
| `1`, `Tab` / `Shift-Tab` | Focus the turns sidebar (below). While the sidebar is hidden they do nothing |

- `Ctrl-b` / `Ctrl-f` are deliberately not bound: `Ctrl-b` is tmux's default prefix.
- Selecting a section scrolls it into view. If the selected section is taller than the viewport, `j`/`k` first scroll through it a page at a time and only then move to the next section.
- Scrolling with page keys or the mouse wheel moves the selection to the topmost fully visible section when the current one leaves the viewport.

**Turns sidebar keys.** The sidebar (§3.2) has its own keymap context, `[keys.turns]` (§7.5), with the same defaults as the selector's lists. `focus_turns` and the pane keys are `browser` actions that hand it the focus.

| Context | Action | Default keys | Effect |
|---|---|---|---|
| `browser` | `focus_turns` | `1` | Focus the sidebar |
| `browser` | `next_pane`, `prev_pane` | `tab`, `shift-tab` | Focus the sidebar |
| `turns` | `up`, `down` | `up`, `k` and `down`, `j` | Select the previous or next entry, and scroll the transcript to it |
| `turns` | `open` | `enter` | Move focus to the selected entry's block |
| `turns` | `next_pane`, `prev_pane` | `tab`, `shift-tab` | Focus the transcript, leaving it as it is |
| `turns` | `focus_transcript` | `right`, `l` | The same |

- `1` and `Tab` in the browser do not affect the selector, where `1` still switches harness and `Tab` still switches pane: the contexts keep them apart. While the sidebar has focus, `1` and `←` / `h` do nothing, matching the selector, where they don't wrap around.
- Selecting an entry **scrolls the transcript to its block**, with the same result as `]` / `[` (one code path): the block's top at the top of the viewport, or as near as the end of the transcript allows, and the transcript's selection on the block's first selectable section. The usual follow rule applies (§6.2): moving away from the bottom stops following. There is no wrap-around at either end.
- A turn can have an entry but nothing selectable, when its text renders to no rows (for example, only an HTML comment). Selecting that entry still scrolls to the block and leaves the transcript's selection unchanged.
- `Enter` does the same and also gives the transcript focus. Focusing the sidebar does not by itself scroll the transcript.
- While the sidebar has focus, other browser keys (`/`, `y`, the fold keys and so on) do nothing. Global keys still work (`q`, `?`, `t`, `Ctrl-o`), and overlays return focus to the sidebar when they close (§1.1).
- The help line shows the sidebar's hints while it has focus, generated from the active keymap: `ENTER to go to block | TAB to switch to transcript`. The help overlay lists the keys in a "Turns sidebar" group.

### 5.4 Copy, save, export

| Key | Action |
|---|---|
| `y` | Copy the selected section **as displayed** (folded: summary line; unfolded: everything shown) as plain text |
| `Y` | Copy the selected section's **full content** (description + full input/command + full result), regardless of fold state or truncation |
| `w` / `Ctrl-s` | Save the selected section as displayed to a file |
| `W` | Save the selected section's full content to a file |
| `e` / `Ctrl-e` | Export the session to markdown **as currently folded** (folded sections become their summary lines) |
| `E` | Export the **full** session to markdown (tool calls as `<details>` blocks with fenced input/output) |

- Save and export prompt for a path in the help line. Defaults:
  - export: `./<project>-<yyyymmdd-hhmm>-<short-id>.md`
  - save: `./<project>-<short-id>-<section-kind>.txt` (the kind is `user`, `assistant`, `thinking`, the tool's kind, `system`, `compaction`, `stats`, and for a notice `error` or `notice`)
- Saving or exporting asks for confirmation before overwriting an existing file.
- The rule and the hint of a subagent title row (§4.2) are not part of copied or saved text: `y` and `w` give the description rows without them, so an unfolded subagent's text ends with its result. `Y`, `W`, `e` and `E` never contain the hint.
- Clipboard: `arboard`, falling back to OSC52 when there's no display server or over SSH/tmux. A toast confirms the copy (`Copied 42 lines`).

### 5.7 Resume in harness

`R` (in the browser, or on a selected row in the selector) asks for confirmation, then:
1. restores the terminal;
2. changes to the session's cwd;
3. replaces the Chronoscope process with the harness's resume command (`exec` on Unix; spawn-and-wait on Windows).

Commands are configurable templates (§7.5). Defaults:
- Claude: `claude --resume {id}`
- OpenCode: `opencode --session {id}`. **Verify this flag** before release.

If the cwd no longer exists, show an error and don't resume.

### 5.9 Mouse

- Wheel scrolls the transcript or the list under the pointer.
- Click selects a section or list row. Clicking a section's summary line (or the `▶`/`▼` marker) toggles its fold. Double-clicking a session row opens it. A click on the rule or the hint of a subagent title row (§4.2) is a click on its row: on a folded row it selects the section and toggles its fold, and on the hint's own row of an unfolded one it only selects. The two padding cells that row draws into count as part of it; every other padding cell does nothing. The hint is not a link.
- Click on a harness tab switches to it. Click outside an overlay closes it.
- **Turns sidebar** (§3.2): the wheel selects the previous or next entry, like `↑` / `↓` (no wrap-around), and scrolls the transcript to its block; it does not move the focus. Clicking a selectable row focuses the sidebar, selects that row and scrolls the transcript to its block. Double-clicking a row does what `Enter` does and gives the transcript focus (two presses on the same row at most 400 ms apart). A click on `Start`, `End`, a connector, a blank row of the pane, the border or the margin does nothing. Clicking the transcript gives it focus.
- Mouse events go to the component under the pointer (§1.1).
- Mouse capture can be disabled in config (`mouse = false`). Most terminals also bypass mouse capture while `Shift` is held, which allows native text selection; the help overlay mentions this.

## 6. Live updates

### 6.1 Mechanisms

| Harness | Change detection | Incremental read |
|---|---|---|
| Claude | `notify` watch on the session `.jsonl` (and its `subagents/` dir) | Read from the last byte offset. New lines go through the same turn assembly (§4.1), so a line extending an existing `message.id` or delivering a `tool_result` updates sections in place. Keep a trailing partial line in a buffer until its newline arrives. If the file shrinks or is replaced (size < offset or inode change), reload it. |
| OpenCode | `notify` watch on `opencode.db` and `opencode.db-wal`, debounced 200 ms; poll every 1 s if watching fails, and always on macOS, where writes to a file that stays open raise no events (the session index polls there too) | `SELECT … FROM session_message WHERE session_id = ? AND seq > ?`, plus re-reading rows whose `time_updated` changed (streaming messages are updated in place) |

- The database is opened read-only (`SQLITE_OPEN_READ_ONLY`). Chronoscope never writes to any harness store.
- Watch events are coalesced. Workers parse new data off the UI thread and send `ModelUpdate`s; the UI thread applies them (§1.1) and redraws at most every 50 ms.

### 6.2 Browser behaviour

- **Follow when at bottom:** if the viewport is at the end of the transcript, new content scrolls into view automatically. If the user has scrolled up, the position is kept and a `↓ N new` indicator appears in the help line; `G` / `End` jumps to the end and resumes following.
- Updates to content already displayed (e.g. a tool result arriving for a pending tool call, or a streamed message growing) update the section in place. The current selection and fold states are preserved.
- The turns sidebar (§3.2) gets the same updates and rebuilds only the rows of the turns they name: an appended turn adds a row, and an Assistant turn gains its duration in place once its stats are known. Neither moves the sidebar's selection, and while the transcript follows the end its selection is tracked.
- A `● live` marker is shown in the browser header while the session is active: file/rows modified within the last 60 s, or OpenCode `time_idle` is null.

### 6.3 Selector behaviour

- Project and session lists update live: new sessions appear, and titles and stats refresh (the panels of §3.1 with them). The current selection is kept (matched by id, not by index).
- Active sessions show the `●` marker in their row.

## 7. Configuration & theming

### 7.1 Theme model

Two layers, modelled on ratcn's shadcn-inspired `Theme`:

1. **Base roles** (required in a theme file): `name`, `foreground`, `muted_foreground`, `background`, `surface`, `field`, `primary`, `primary_foreground`, `secondary`, `secondary_foreground`, `accent`, `destructive`, `destructive_foreground`, `warning`, `border`, `ring`, `cursor`.
2. **Component tokens** (optional overrides; each derived from a base role by default): see the table below.

| Token | Default | Used for |
|---|---|---|
| `user_title` | `primary` | `User` block title |
| `assistant_title` | `accent` | `Assistant` block title, model @ effort |
| `system_title` | `muted_foreground` | System / compaction block titles |
| `timestamp` | `muted_foreground` | Right-aligned block titles |
| `tool_description` | `foreground` | `> description` lines |
| `label` | `muted_foreground` | `Command:` / `Result:` labels |
| `command` | `foreground` | Command / tool input text |
| `output` | `muted_foreground` | Tool results |
| `error_output` | `destructive` | Failed tool results, error notices |
| `diff_added` / `diff_removed` | `primary` / `destructive` | Edit diffs |
| `thinking` | `muted_foreground` | Thinking text |
| `selection_marker` | `primary` | `▒` and `>` markers |
| `search_match` | fg `primary_foreground` on `primary` | Search hits (the only explicit background colour; the selector's focused selection uses reverse video, §7.2) |
| `help_key` / `help_text` | `primary` / `muted_foreground` | Help line and help overlay |
| `toast` | fg `foreground` on `surface` | Toast notifications |
| `syntax.*` | derived from `accent`, `primary`, `secondary`, `warning` | Code-block syntax highlighting |

Colours accept `#rrggbb`, ANSI names (`red`, `bright_blue`, …), ANSI indices (`0`–`255`) and `reset` (terminal default).

Per-theme option `transparent_background` (bool): when true, `background` is not painted and the terminal's own background shows through. Users can override it per theme in config.

### 7.2 Emphasis rules

Selection is shown with **text brightness and markers**. The one background band is the session selector's focused selection:

- Unselected list rows and transcript sections: `muted_foreground`.
- Selected transcript section and theme-selector row: `foreground`, bold, with a marker (`>` in the theme list, `▒` over the left border in the transcript) in `primary`.
- Session selector (Projects and Sessions lists):
  - Selected row in the **focused** list: the `>` marker in `primary`, never inverted. Everything after the marker is one **inverted** band (`foreground` with the reverse-video modifier, not bold), running up to the row's right margin (two cells before the pane border). Inside the band, the timestamp, live dot, title, gaps and stats all take the band's style.
  - Selected row in the **unfocused** list (e.g. Projects while Sessions has focus): text **bold** in `secondary_foreground`, not inverted; the `>` marker in the same `secondary_foreground` (not bold), so the context stays visible.
- The turns sidebar (§3.2) selects the same way, with `▒` as its marker: in a focused sidebar the `▒` in `primary` and one inverted band after it; in an unfocused one the `▒` and the bold text in `secondary_foreground`. Its `┬`, `├`, `┴`, `│` and `╶` are `muted_foreground`.
- Focused pane border: `ring`; unfocused borders: `border`.
- The rule of a subagent title row (§4.2) is drawn in `border`, whatever the selection and `dim_unselected`. It is never dimmed and never bold. Its hint follows the section like any other text: `muted_foreground`, bold when the section is selected.
- Selected harness tab: `primary`, underlined; other tabs: `muted_foreground`.
- In the transcript, dimming of unselected sections is controlled by `dim_unselected` (default `true`). When `false`, all sections use their normal token colours and only the marker + bold indicate selection.

Compiled into the binary:

```
╭─ Themes ──────────────────────────────╮
```

- Opened with `t` from the browser or the selector. It is a small centred overlay drawn on top of the current screen, so the preview is visible on real content around it.

### 7.5 Config file

- Location: `$XDG_CONFIG_HOME/chronoscope/config.toml` (`~/.config/chronoscope/config.toml`), via `etcetera`. On macOS the XDG-style path is used as well, so dotfiles stay portable.
- All keys are optional. A missing file means defaults.
- Unknown keys produce a warning (shown once as a toast), not an error.
- Invalid values fall back to the default with a warning.
- Changes are picked up on restart; hot reload is future work.

```toml
theme = "tokyo-night"
transparent_background = false   # overrides the theme's setting when present
mouse = true
show_system = true
dim_unselected = true
timestamp_format = "%Y-%m-%d %H:%M:%S"   # strftime; displayed in local time
utc = false
truncate_output_lines = 200

[harness.claude]
enabled = true
data_dir = "~/.claude/projects"            # override auto-detection
resume_command = "claude --resume {id}"

[harness.opencode]
enabled = true
db_path = "~/.local/share/opencode/opencode.db"
resume_command = "opencode --session {id}"

[projects.aliases]
"/home/jacob/Development/projects/brio" = "BRIO"
"/home/jacob/Development/projects/camera-settings" = "CameraSettings"

[keys.browser]                 # action = key or [keys]; replaces the default for that action
fold_toggle = ["enter", "space"]
copy = "y"
copy_full = "Y"

[keys.selector]
search = "/"

[keys.turns]                   # the turns sidebar while it has focus
open = "enter"
```

Key bindings are grouped in contexts, one `[keys.<context>]` table each: `global` (quit, help, theme selector, open the selector), `browser`, `selector`, `overlay` (the help and details overlays and the theme selector) and `turns` (the turns sidebar, §5.3). Apart from the global keys, components resolve a key in their own context only, which is why the same key (`1`, `Tab`) can mean different things in the browser and in the selector. The `turns` defaults match the selector's lists:

| Action | Default keys |
|---|---|
| `up` | `up`, `k` |
| `down` | `down`, `j` |
| `open` | `enter` |
| `next_pane`, `prev_pane` | `tab`, `shift-tab` |
| `focus_transcript` | `right`, `l` |

`focus_turns` (`1`), `next_pane` (`tab`) and `prev_pane` (`shift-tab`) in `[keys.browser]` focus the sidebar, and `details` (`i`) opens the details overlay (§3.3).

Key syntax: `a`, `A`, `ctrl-d`, `shift-tab`, `enter`, `esc`, `pgdn`, `f5`, and two-key chords as space-separated keys (`"g g"`; only in user config, in the `browser`, `selector` and `turns` contexts, since no default binding is a chord). The help overlay is generated from the active keymap, so it always reflects the user's remappings.

### 7.6 Timestamps

- Displayed in local time using `timestamp_format`. With `utc = true`, UTC is shown with a `Z` suffix.
- The selector's session rows use the same format without seconds.

### 8.2 Scale & performance

Target: sessions up to **~100 MB** stay smooth.
- Parsing is streaming (line by line for JSONL, paged queries for SQLite) and runs off the UI thread. The UI shows a loading state and becomes interactive as soon as the first screen of content is parsed.
- Large tool outputs: the model stores line counts and byte ranges up front. The full text is materialised only when the section is unfolded, searched, copied or exported.
- Detail fields are not parsed while assembling. A turn keeps only a byte range or row id per section (§4.1), and opening the details overlay re-reads one or two lines (Claude) or rows (OpenCode) on the UI thread, which takes about a millisecond even for a 2 MB result (a line of about 4 MB; measured for Claude). `toolUseResult`, which can hold whole files, is read by the assembler and the details overlay through a typed head and never loaded as a whole value. (Finding a subagent's transcript from its parent, when no meta file names the call, scans the parent for the call's result line and loads its `toolUseResult` as a value, §4.4.)
- The turns sidebar (§3.2) builds its rows from the section derivation, never from a layout or a render, and a turn update rebuilds only the rows it names. A key press in the sidebar (selection, transcript scroll and frame) is held to the frame budget below.
- Layout is computed lazily per block for the current width. Only blocks overlapping the viewport are rendered.
- Session stats (`SessionStats`, §4.1) are computed in the background, on a small pool of worker threads, and cached in `$XDG_CACHE_HOME/chronoscope/stats-v2.json`: one JSON file mapping a harness's stats key to the stats computed for it, with both durations in milliseconds and the `TokenUsage` serialised. The previous version's file is removed, best effort, when the cache loads, and never read, so every session's stats are computed once again after an upgrade (without this, sessions that have not changed would keep showing their old row, because their keys still match). Entries of sessions that are gone are pruned. The key must see everything the stats count, subagents included:
  - Claude: `claude:<path>:<size>:<mtime>:<n>:<total size>:<newest mtime>`, with the main transcript's size and mtime (nanoseconds since the epoch) followed by the number of subagent transcripts (§2.1), their total size and their newest mtime (`:0:0:0` without subagents). A main file that cannot be stat'ed gives `claude:<path>:missing`. The key runs on the coordinator thread, so it stats files but never reads them, and a listing problem there is only logged at debug level.
  - OpenCode: `opencode:<db path>:<session id>:<time_updated in ms>`, where the time is the newest `time_updated` of the session and of all its descendants (at least the session's own). It comes from the last index build, which aggregates it for all sessions with one recursive query. A descendant whose `time_updated` is not an integer is left out of that aggregate, and a failure of the query is logged and never fails the index.
- **The subagent files are memoised.** A session with many subagents (the largest local session has 320 files of 207 MB in total) is recomputed on every coalesced rebuild while it runs, which can be for hours. So each subagent file's usage is kept in memory, keyed by (path, size, mtime) as discovery does for its scans, with the size and mtime taken from the listing before the file is read, so a file that grows during the read is read again next time. A recomputation reads the main transcript and only the files that changed. Entries for files that are gone are dropped, as are those of sessions that are gone, and a failed read is not memoised, so it is tried again next time. The first computation parses all the files (about 0.5 s for that session with the files in the OS cache) on the stats pool, which is background work. `doc/performance.md` records the figures.
- **The stats are refreshed even when the snapshot is not.** A write to a subagent file (or to an OpenCode child row) changes no summary of the main session, so a rebuild finds the snapshot unchanged and does not send it to the UI. The stats are still rescheduled, over the sessions of the last snapshot, whenever a rebuild succeeds, because a session's key may have changed. A failed build (a poll that could not read the store) schedules nothing. The file watcher already reports these writes, because it watches the data directory recursively.
- Session discovery reads each Claude transcript at most once per index build. Each file's scan result (cwd, start time, first prompt, last `ai-title`) is kept in memory, keyed by (path, size, mtime). The initial build and live rebuilds rescan only new or changed files, scanning several files in parallel. Results for files that are gone are dropped.
- Budgets (measured with benchmarks and an ignored budget test on a synthetic 100 MB fixture, `doc/performance.md`):
  - first content within 300 ms;
  - full parse under 2 s;
  - each frame rendered in under 16 ms;
  - memory use within roughly 3× the file size.

### 8.3 CI & releases

- Hosted on GitHub.
- CI: GitHub Actions runs `cargo fmt --check`, `cargo clippy -- -D warnings` and `cargo test` on `ubuntu-latest`, and separately on `macos-latest`. Only the Linux result gates test bundles and releases, because macOS runners are often unavailable; a release without a macOS result has no macOS files.
- Releases: tagged builds run CI, then produce binaries for x86_64 Linux and aarch64/x86_64 macOS, plus `.deb` and `.rpm` packages for Linux, and attach them to a draft release (see `doc/releasing.md`).

### 8.4 Terminal environment

Primary environment: inside terminal multiplexers (**tmux**, **herdr**).

- Clipboard: try `arboard` first. When no display server is reachable or `$TMUX` is set, also emit OSC52.
  - Under tmux, wrap OSC52 in the DCS passthrough sequence.
  - Document `set -g set-clipboard on` and `set -g allow-passthrough on`.
  - herdr's OSC52 behaviour must be verified.
- `Esc` responsiveness: document tmux `set -sg escape-time 10` (the default 500 ms makes `Esc` feel laggy).
- No feature depends on the kitty keyboard protocol or on modifier+Enter. Every default binding works with legacy key encoding.
- Colours: truecolor is assumed when `$COLORTERM` is `truecolor`/`24bit`. Otherwise hex colours are mapped to the nearest xterm-256 colour. The `terminal` theme uses only ANSI colours.
- Respects `NO_COLOR` by falling back to the `terminal` theme with styling (bold, underline, reverse) only.

### 8.5 Robustness

- Never writes to harness data. The SQLite database is opened read-only.
- Unknown entry types, unknown content blocks and malformed lines are skipped and counted, not fatal. Every field is optional and unknown fields are ignored. While assembling, a known field of another JSON type fails its line (OpenCode: its row), which is then skipped and counted like a malformed line (for example Claude `timestamp`, `message.id`, `message.model`, `cwd` and `durationMs`, or OpenCode `time` and `cost`). Fields read leniently count as missing instead: Claude `message.usage` and its counts, `message.stop_reason`, both `isApiErrorMessage` fields and `toolUseResult`; OpenCode `tokens`, `finish` and `error`. The details overlay's re-read tolerates a wrong type in every field it reads, and a bad value only drops its row.
  - A muted `N entries could not be parsed` note appears in the browser header.
  - Session metadata entries (known ones such as `agent-name`, `queue-operation`, `continued-in`, `bridge-session`, `tools-used`, and unknown types without a `message`) carry no conversation content: they are skipped and logged, but not counted in the note.
  - Details are written to a log file at `$XDG_STATE_HOME/chronoscope/chronoscope.log`.
- The schema version is checked on open (OpenCode `migration` table / Claude `version` field). An unknown newer version logs a warning, and Chronoscope still tries best-effort parsing.
- Terminal state is always restored on exit, panic or signal (panic hook + raw-mode guard).

## 9. Out of scope / future

Future work (not v1):
- Codex and Pi adapters. Their tabs are hidden until implemented.
- Hot reload of config and theme files.
- Full-text search across all sessions (needs a background index).
