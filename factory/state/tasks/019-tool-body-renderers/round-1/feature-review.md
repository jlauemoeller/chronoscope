## Findings
1. [must-fix] The Subagent `Result:` is never truncated. In `src/components/turn_block/renderers/tool/subagent.rs`, `SubagentBody::body` always returns `remaining: None`. The goal says "Long results are truncated at `truncate_output_lines`", and the planner note says "When a body's result has more than `truncate_output_lines` lines, only the first N lines are shown…". Nothing in task.md exempts Subagent. The build notes give the exemption only under Changes, not as a spec-silent judgement call. A long subagent report is therefore drawn in full, with no `… N more lines` stop. Change:
   - In `SubagentBody::body`, cut the result's source text with `truncate_lines(&text, limit(ctx))` before `render_markdown`, so lines are counted logically before wrapping. Return `remaining: (cut > 0).then_some(cut)`.
   - Then fix the row order. `ToolCallSection::render` (`tool/mod.rs`) pushes `body.hint` before the more row, and then pops the last line as `ToolRendered::more`. As it stands, the more row would land below `a to open transcript`. Reorder `render` so the more row directly follows the result content and the hint comes after it, and keep the more row as the separate stop. For example, have the widget insert the hint after the more row, or return the hint apart too. The widget's span bookkeeping in `widget.rs` `layout` must still put the more row directly after the tool section's lines, with the hint rows inside the tool section's span (or after the more row), so that heights still match.
   - Add a unit test in `subagent.rs`: a 10-line result with `truncate: 4` gives 4 result lines and `remaining == Some(6)`, and `expanded: true` shows all 10. Add a layout test checking that the more row is directly below the last result line and that the hint still renders. The property test already generates Subagent calls with small limits, so it will check the heights.
2. [nit] A failed Write or Edit call shows no error (`edit.rs` and `write.rs` never read `call.result`). An Edit that failed with "old_string not found" renders the intended diff as if it had been applied, and a pending Write or Edit shows no `(pending)`. The table lists no `Result:` for these kinds, so this does not breach the spec. Change, optionally: when `call.status` is `Error` or `Pending`, append the usual `result_block("Result:", call, ctx)`, so the error appears in `error_output` and pending appears as `(pending)`.
3. [nit] Read detects Claude numbering only from the first line (`read.rs`, `numbered`: `lines.first().and_then(parse_numbered)`). Numbered output that starts with an unnumbered line, such as a leading notice, gets numbered a second time. Change: detect on the first non-blank line, or on a majority of lines, rather than only `lines[0]`.
4. [nit] OpenCode's read output format (`00001| text` inside `<file>…</file>`) is not parsed into the gutter, so OpenCode reads show two sets of numbers. The planner note only names Claude's formats, so this is outside the criteria. Change, optionally: accept a `|` separator in `parse_numbered`, and skip the `<file>`/`</file>` wrapper lines.
5. [nit] When a lazy Read output fails to materialise, `ReadBody::body` calls `ToolOutput::text()` twice: once via `.ok()`, which discards the error, then again inside `result_block`, which logs it. That means a second disk read on the error path. Change: keep the `Result` from the first call, and pass the error to a shared "unavailable" block helper rather than re-reading.
6. [nit] `range_note` (`read.rs`) gives the requested range (`offset + limit - 1`), not the range actually returned. A short file read with `limit: 2000` shows `(lines 1–2000)`. Change, optionally: cap the end at `offset + shown_line_count - 1` once the content is known.
