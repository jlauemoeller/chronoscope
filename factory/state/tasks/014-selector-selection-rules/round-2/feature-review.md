## Findings
1. [nit] `src/app/selector.rs` `settle_preselection`: the preselection window now stays open for as long as the shown harness has no projects. Example: Claude is available but its data dir is permanently empty, OpenCode has projects, and nothing matches. `preselecting` then stays `true` until the user sends a `SelectorMsg`. During that time, an OpenCode live snapshot that adds a project matching the working directory moves the selector to OpenCode while the user is looking at it, or while help or the theme selector is open, because those do not end the preselection. This is consistent with "before the user has acted" and is not a spec breach. Change, if wanted: state this in the doc comment of `settle_preselection`, or end the preselection on any user key or mouse event, not only on a `SelectorMsg`.
2. [nit] `src/app/selector.rs` `SelectorState::harness_empty` and the test `a_harness_with_projects_but_no_sessions_shows_an_ordinary_empty_list` (`src/app/selection_tests.rs`). `data.projects.is_empty()` is narrower than the acceptance criterion and planner note, which say "a harness with zero sessions". A harness that lists projects but has no sessions in any of them now shows a normal project list and no `No sessions for this harness` message. The new test locks that in. Today only the Claude adapter exists (`src/harness/` has only `claude/`), and its `build_index` creates projects only from sessions, so this cannot be reached and the AC holds. An adapter whose projects come from somewhere else, such as OpenCode's `project` table, can reach it. Change: no code change now. Record in the doc comment of `harness_empty` that it assumes "no sessions" implies "no projects". The first adapter task that can produce projects without sessions must either draw the full empty state (no project rows, ` Sessions ` title, empty Working Directory box) or get the planner to confirm the narrower rule.
