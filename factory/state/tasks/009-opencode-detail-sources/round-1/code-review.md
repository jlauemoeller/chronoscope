## Summary
The OpenCode details reader, row references and shared error text are well built, and the acceptance tests are effective: the assembler's parse is unchanged, and only the two new App-level `.snap` files were added. One must-fix remains: a single non-object part in a row's `content` makes every tool call of that row show a false `unavailable` and lose its `start`, although the row is readable and the assembler renders those calls normally. The test gate passes, and the budgets also pass on my run (`cargo test --release -- --ignored budgets --nocapture`: full parse worst 142.9 ms and 318.3 ms, one endless turn 680.0 ms, peak heap 0.22x and 0.63x, frames worst 3.71 ms).

## Findings
1. [must-fix] `src/harness/opencode/details.rs:199-215` (`find_part`) and `:298-301` (`ToolHead`) — `ToolHead.content` is `Option<Vec<PartHead>>`, so one sibling part that is a number, string or `null` fails the whole `Vec`. For `"content":[5,{"type":"tool","id":"call-1",...}]`, `find_part` returns `None` and the Tool call group is `unavailable`, with no `start`. The assembler reads the same row as `Vec<Value>`, skips the odd part and shows `call-1` normally (`assemble.rs:137`, `:728-743`). This contradicts §5.3 and the planner's list of unavailable causes (database gone, row deleted, `data` not parseable), the planner's "tolerant heads", and §9.5 (changed harness data degrades). The build notes record this as a decision, but the spec doesn't allow it. An array part is also read positionally as a struct, because `PartHead` has no object check. Change: read `content` per element, keeping each element's position so the `<row id>:<index>` fallback still matches. For example, use a `#[serde(transparent)]` newtype around `Option<PartHead>` with `deserialize_with = "lenient_object"`, and match only the `Some` elements in `find_part`. Add a test to `src/harness/opencode/details_tests.rs`: assemble `FULL`, then `set_data` the row to `content` with `5`, `null`, a string and an array before the tool part. Assert that the Tool call group has `start`, `duration` and `status` and no `unavailable`, and that a tool part without an id is still found by its original index.

[nit] `src/harness/opencode/details.rs:49-55` — when the turn's row is also the section's row (the first assistant row, so the common case), the same `SELECT` and `Head` parse run twice, and `find_part` parses `data` a third time for a tool call, all on the UI thread (`src/app/details.rs:23-25`). Change: read each distinct row id once, and parse the head and the tool parts in one pass.
