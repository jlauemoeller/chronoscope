[must-fix] `src/harness/opencode/details.rs:219-238` (`find_part`) and `:329-335` (`PartHead`) — the doc says it finds the part "the way the assembler names it", but it differs in two ways, and both break the planner note that a tool part's start has "the same source as the duration in `tool_call`". First, it has no type check: `part_item` (`assemble.rs`) only uses a part's `id` when `type` is `tool`, while `find_part` matches any part. Second, it takes the first match: `apply_assistant` upserts a row's parts in order, so the last part with an id replaces the earlier one, and the item shows that last part. Confirmed by a throwaway test in a copy of the branch outside the repo. With `content` holding tool `c1` twice (1 s, then 5 s about 8 minutes later), the group shows `start 22:13:21Z` from the first part and `duration 5s` from the second. With a text part `{"type":"text","id":"c1","time":{"created":1600000000000}}` before tool `c1`, it shows `start 2020-09-13 12:26:40Z` from the text part and `duration 1s` from the tool. Both inputs are unusual data, and neither is in the fixture. This is the within-one-row form of round-1 feature finding 1. Change: add `#[serde(default, rename = "type", deserialize_with = "lenient")] kind: Option<String>` to `PartHead`. In `find_part`, call `.rev()` after `.enumerate()` so that the index stays the original position, and keep only parts with `kind.as_deref() == Some("tool")` before `.find(...)`. I tried this change in the same copy: both cases then give `start` and `duration` from one tool part, and all `harness::opencode` lib tests still pass. Add a test to `src/harness/opencode/details_tests.rs` with both inputs, asserting the `start`, `duration` and `status` rows of the Tool call group come from the one tool part the item shows.
