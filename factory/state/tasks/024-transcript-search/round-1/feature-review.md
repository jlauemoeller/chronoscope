One behaviour bug remains. `reveal_match` maps a match to a rendered row, and decides whether to expand truncated output, by counting the query's hits in the section's *rendered* rows. ## Findings
1. [must-fix] Jumping to a match (`reveal_match`/`occurrences` in `src/components/transcript/search.rs`) uses the k-th hit of the query in the section's *rendered* rows. These rows include text that is not in `section_text`, such as the `Command:` and `Result:` labels of a tool body (and gutters or markers of other renderers). The consequences:
   - A match beyond `truncate_output_lines` is not expanded when the query also hits rendered chrome. That breaks the binding planner rule "A match beyond the truncation limit also expands the output temporarily".
   - Even without truncation, the jump scrolls to the wrong row.

   Reproduction: in a scratch copy I used the `long_log` fixture with line 350 = `the final result here` (limit 200) and searched `result`. The result is `1/1`, but `folds.is_expanded(c1)` is false and the screen shows `Result:` and `line 1..20`. The real hit is never revealed, and the label is the only thing highlighted. The same happens with `command`. Change:
   - Decide `temp.expanded` from the match itself, not from rendered hit counts. Expand when the match's `line` lies in the tool-output portion of `section_text` at or past the truncation limit. To support this, make `tool_text` expose the line where the output starts, or store it in `Match`.
   - Pick the scroll row from that position too, for example the output's first rendered row plus the output line offset. Alternatively, restrict `occurrences` to rows that render `section_text` content.
   - Add a component test in `src/components/transcript/tests/search.rs`. Query `result` (and `command`) on a Shell call whose only real hit is past the limit. Assert that the output expands and that the hit's row is on screen after the jump.
2. [nit] `printable_keys_go_into_the_prompt_and_trigger_no_action` (`src/app/browser_tests/search.rs`) checks `n` with `position == None`. That cannot fail, because without an active search `n` is a no-op even if it reached the transcript. `t` is bound to `Theme` (global), not to toggle-system, so the `SHOW_SYSTEM_ATTR` assertion does not test what `t` would do. The `q` check and the inserted text are real checks. Change: run a search first and assert that the position stays `1/5` after typing `n`. For `t`, assert that no theme selector or overlay is opened, or that the screen is unchanged.
3. [nit] Highlighting is applied per rendered row by text, so chrome such as `Result:`/`Command:` labels is highlighted for queries like `result`, although it is not search text. This has the same root cause as finding 1. If finding 1 restricts rows to content rows, consider using the same restriction in `TurnBlock::highlight`.
4. [nit] `occurrences()` runs an uncached `layout()` of the block up to three times per jump (`reveal_match`). On a very large expanded output each `n` re-lays it out several times on the UI thread. Consider using the cached layout via `self.cache`/`measured`.
5. [nit] Interpretation of the `Enter` criterion: while a section is only temporarily unfolded, the first `Enter` changes nothing visible (it makes the unfolding explicit), and only a second `Enter` folds. This matches the AC's literal wording and is documented in the build notes. Flagging it so the Approver knows `Enter` appears inert once in that state.
6. [nit] `Enter` on a section that the search only *expanded* (it was already unfolded by the user) folds it via the normal toggle, but `fold_command_on_temp` drops the temp state without clearing the search's expansion. The output stays expanded the next time the user unfolds it. Change: in `fold_command_on_temp`, clear the expansion (`folds.clear_expanded`) when `temp.expanded` and the command folds.
