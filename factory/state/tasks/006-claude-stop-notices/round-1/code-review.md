## Findings
1. [must-fix] `src/harness/claude/assemble.rs:837` — The key for a flagged message's text block is `api_index.unwrap_or(0) + i`. Without `apiBlockIndex`, every one-block line gets key 0, so each new block overwrites the previous one and its text is lost. Two flagged lines of one message with the texts `first` and `second` give the notice `"second"`; the same lines with `apiBlockIndex` 0 and 1 give `"first\nsecond"`. This breaks the binding planner note ("the message's text blocks joined with newlines"). Base spec §3.1 describes this one-line-per-block layout, and the doc comment on `block_id` names the no-index case and handles it for ordinary text. `the_text_blocks_of_an_api_error_are_joined_with_newlines` passes only because it puts both blocks on one line. Change: keep the current key when `api_index` is present. When it is absent, a text that equals or extends a block already stored for the message replaces that block, and any other text gets the next key after the highest stored one. This keeps repeated lines collapsing, including a repeated line with several blocks. Add a test to `tests/claude_notices.rs`: two flagged lines of one message, no `apiBlockIndex`, different texts, expecting one `Error` notice with `first\nsecond`. `an_api_error_repeated_over_several_lines_gives_one_notice` must keep passing.

2. [must-fix] `src/harness/claude/wire.rs:69` (with the check parse at `wire.rs:274`) — `Entry.is_api_error_message` is read with `lenient`, whose `RawValue` requires valid UTF-8. The fallback check in `lenient_entry` parses `Entry<MessageWithoutUsage, IgnoredAny>`. That type skips the fields inside the message but still reads this entry-level field, so the check fails and the line is lost. Probe line: `"isApiErrorMessage":"x\xffy"` at the top level with an ordinary text block. On `main`: `unparsed_count() == 0` and the text is shown. On this branch: `unparsed_count() == 1` and the text is gone. The same bad byte in `message.isApiErrorMessage` or `message.stop_reason` keeps the line parsed. This is an unexpected JSON type failing the line, which the planner note and the acceptance criterion rule out, and it changes an outcome the `invalid_utf8_outside_usage_keeps_its_outcome` test in `tests/claude_assembly.rs` pins for unknown top-level fields. Change: make the check parse skip this field, for example with a third type parameter on `Entry` for the flag, as `M` and `T` already do for the message and `toolUseResult`. Add a case to `invalid_utf8_outside_usage_keeps_its_outcome` or to `tests/claude_notices.rs` with a bad byte inside a top-level `isApiErrorMessage` string, expecting the line parsed, its text kept, no notice and `unparsed_count() == 0`.

3. [nit] `src/harness/claude/assemble.rs:809-839` — The flag is sticky per message id only from the first flagged line on. If an unflagged line of a message comes first, its `Item::Text` stays beside the later notice, so `API Error: 500` on an unflagged line then a flagged line is shown twice, and that earlier text is not part of the notice. When the lines come in the other order, only the notice appears. The spec does not describe a message flagged on only some of its lines, and no local transcript has one, so this is not a must-fix. Change, if wanted: when the flag first appears for a message id, move that message's existing text items into `error_text` and take them out with the new `remove` helper, with a test for the order.
