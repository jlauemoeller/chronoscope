## Summary
The registry, the index worker (snapshots, notify watching with 500 ms coalescing, 2 s polling fallback), the stats pool, the on-disk cache and `is_active` all match the task and planner notes. Every acceptance criterion has a test that would fail if the behaviour were wrong, and the gate passes: fmt clean, clippy clean, all tests green. One reachable race lets an older stats result overwrite a newer one for a live session, which is wrong behaviour. Its fix is small.

## Findings
1. [must-fix] An older stats result can overwrite a newer one. `pending` only dedupes identical `(harness, key)` pairs, and `Queue::replace_with` drops only *waiting* jobs. So when a live session's file grows while its old job (key K1) is running on one pool thread, the new job (K2) can start on another thread. `Coordinator::record` (`src/index/worker.rs`, around lines 446-468) sends whatever finishes and sets `sent[(h, id)] = K1`, without checking that the key is still current. If K1 finishes after K2, the UI is left showing the older stats. Nothing corrects this until some later rebuild of that harness, which may never come if that was the session's last write. Change: in `record`, after the error branch, do not send or cache the result unless `self.harnesses[done.harness].live_keys` contains `done.key`; return `true`. Add a test, for example a harness stub whose `stats` blocks on a barrier for the first key, checking that a stale result arriving last is not sent.
2. [nit] `schedule_stats` (`src/index/worker.rs`, the `self.sent.retain(... sessions.values().flatten().any(...))` call) is O(sessions²) on every rebuild, and during live use that is about every 500 ms. Change: collect a `HashSet<&SessionId>` of the snapshot's sessions once and test membership against it.
3. [nit] `StatsCache::write` (`src/index/cache.rs`) always writes to the same `stats-v1.json.tmp`. Two Chronoscope instances (two tmux panes, §9.4) can interleave their writes and leave a partial file, which is then ignored as corrupt and recomputed. Change: use a unique temp name in the cache dir (`tempfile::NamedTempFile::new_in(dir)?.persist(...)`, or a pid suffix).
4. [nit] In `Coordinator::build`, `log::error!("could not build the {} index …")` runs on every failed rebuild. A data dir that exists but can't be read (permission denied) can't be watched either, so it falls back to polling and logs an ERROR every 2 s indefinitely. A missing dir is fine, because `list_transcripts` maps `NotFound` to an empty list. Change: log repeated build failures once per harness, as `warned_watch` already does for watching.
5. [nit] Every change to a live session queues a full re-parse of it: up to 3 concurrent parses of the same large file, one new parse per 500 ms rebuild. This follows the planner's "only for sessions whose key has no cached value" rule, but it is wasteful on 100 MB live sessions. Consider skipping a new job while a job for the same session id is still running, and re-queueing when that job finishes.
6. [nit] `IndexHandle::drop` only signals the worker to stop. If the process exits right after dropping the handle, the "save on shutdown" never happens. The docs point at `shutdown()`. Change: say explicitly in the `IndexHandle` docs that the App must call `shutdown()` on exit (task 013) so the final cache save is guaranteed.
7. [nit] `tests/index.rs::dropping_the_handle_stops_the_worker_and_disconnects_the_receiver`: the comment says "changes cause nothing", but the test makes no change and asserts nothing about it. Change: trim the comment, or append to a fixture after the disconnect and assert nothing happens (for example, that the cache file is unchanged).
8. [nit] Stats `duration` only counts timestamps on entries that the assembler parses (user, assistant, some system and attachment entries). Timestamped noise and metadata entries are not counted. That reading of "entry timestamp" is reasonable, but it should be stated in the `Harness::stats` / `ClaudeHarness::stats` docs.
