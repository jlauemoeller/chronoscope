## Findings
1. [must-fix] `src/components/details_overlay/mod.rs:140-142` — A `details` key bound to a chord does not close the overlay. Chords are legal in the `browser` context (`Context::supports_chords`, spec/SPEC.md §8.5) and the transcript opens with one because it uses `KeyResolver::feed`, but `DetailsOverlay::on` uses `Keymap::resolve`, which by its own documentation does not consider chords. This breaks SPEC §5.1 ("The `details` key also closes it") and the criterion "A remapped `details` key opens and closes the overlay". Reproduced with a throwaway app-level test on a copy of the branch: with `details = "z i"`, `z` `i` opens the overlay, and pressing `z` `i` again leaves it open; only `Esc` closes it. The help overlay has no such problem, because the `global` context rejects chords. Change: give `DetailsOverlay` a `KeyResolver::new(Context::Browser)` field. In `FrameKey::Unbound`, call `feed` and answer `Msg::CloseDetails` on `Resolved::Action(Action::Details)`. For every other `FrameKey` result, call `reset` so an overlay key drops a pending prefix. Add an app test in `src/app/browser_tests/details.rs` that opens and closes with `"z i"`, and a component test that a lone `z`, or `z` followed by another key, does not close it.
