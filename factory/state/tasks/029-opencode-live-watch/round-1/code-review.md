VERDICT: FAIL

## Summary
The session follower is well built. It watches the parent directory with a name filter, debounces events, falls back to polling, replaces rows in place with per-row stat contributions so stats are not double-counted, routes every query through the select-only helper, and stops promptly. Its integration tests use a separate writer connection and assert the right things. The selector index is the problem. It still watches `opencode.db` and `opencode.db-wal` as individual files, so it loses live updates for good once OpenCode deletes and recreates the WAL. That breaks the task goal "the selector's index also refreshes OpenCode lists live" (§7.3).

## Findings
1. [must-fix] `src/harness/opencode/discovery.rs:211-213` (`watch_paths`), together with `src/index/worker.rs:356-379` (`start_watching`) and `src/index/worker.rs:630-648` (`watch`): live index refresh for OpenCode stops working after the first WAL deletion.
   - **What happens:**
     - The index puts a `notify` watch on each returned path itself.
     - On Linux, inotify drops a file watch when the file is unlinked. SQLite deletes `opencode.db-wal` when the last connection closes, for example when OpenCode exits.
     - `HarnessState::watcher` stays `Some`, so `start_watching` returns early and `poll_at` is never set again.
     - When OpenCode starts again, it writes new sessions, titles and `time_updated` into a fresh `-wal` that nobody watches. `opencode.db` only changes at a checkpoint (about 1000 pages, or on close), so the session list stays stale until then.
     - The same happens when chronoscope starts before OpenCode. The index polls until both files exist, then watches them, then loses the WAL watch on the next OpenCode exit.
   - **Why the tests miss it:** neither index test removes the WAL. `the_index_delivers_a_new_snapshot_…` runs in rollback mode and polls. `the_index_follows_a_write_ahead_log_database_…` keeps the WAL alive for the whole test.
   - **Why it's in scope:** the planner notes give this exact reason ("the WAL file may be created and removed") for watching the directory. The load worker in `watch.rs` handles it correctly, but the index doesn't.
   - **Change:** make the index survive WAL churn. Either option works:
     - (a) Let a harness ask for a non-recursive, name-filtered directory watch. For example, OpenCode's `watch_paths()` returns the DB's parent directory, and the index watches it non-recursively and filters events by file name the way `watch.rs::forward` does. Don't watch OpenCode's data directory recursively: it holds large, busy subtrees such as `snapshot/`, `log/` and `storage/`.
     - (b) In `index/worker.rs`, re-arm the watcher when an event reports a `Remove` of a watched path, or a watch error. Drop `state.watcher` and call `start_watching(i)`. That falls back to polling while the file is missing and resumes watching once it exists again.

     Add a test in `tests/opencode_live.rs` with a long `Timing.poll`. Start in WAL mode, close the writer so the `-wal` file is deleted (assert that it's gone), reopen a writer, insert into `session_v2`, and expect a `Snapshot` with the new session within 10 s.
2. [nit] `src/harness/opencode/watch.rs:30,127` (`MAX_WAIT`): the 1 s cap goes beyond the binding planner note ("wait until 200 ms have passed without further events, then process once"). The builder disclosed it and gave a good reason: a message that streams without pause would otherwise never appear. It still coalesces on 200 ms of quiet and meets the coalescing AC, so I accept it. Flagging it so the Approver sees the deviation was deliberate. No change needed; the Approver could ask for a one-line mention in SPEC/planner notes.
3. [nit] `src/harness/opencode/follow.rs:244`: `step()` calls `self.asm.finish()` on every pass. Suppose a `synthetic`/`system` row arrives in one pass and the following `user` row in the next. The live view flushes the injected entry into the current Assistant turn, but a fresh reload puts it at the start of the new User turn. So the live state can differ from a reload. Change: flush held entries only when the session is idle, or add this to the "Known limits" in the build notes. Optionally add a test.
4. [nit] `src/harness/opencode/assemble.rs:704` (`upsert`) used from `replace_row` (`:520`): when the latest row updated in place gains content in a part at a lower index that was skipped before (empty `text`/`reasoning`), the new item is appended after the row's higher-index items. A fresh load would place it before them. This is not the "older row" case in the build notes. Change: in `apply_assistant` with `new == false`, insert unseen items after the last existing item of the same row (by `row.id:` prefix / part index) instead of at the end, or document the limit.
5. [nit] `src/harness/opencode/assemble.rs:520` (`replace_row`): an assistant/user row whose `data` failed to parse when first pushed has no `row_turn` entry. If it later becomes parsable, it is ignored forever, and it stays in `unparsed`, so `ParseWarnings` never drops. Change: in `replace_row`, when `row_turn` has no entry but the row id is in `unparsed`, log it, or remove it from `unparsed` on a successful parse. Alternatively document the limit.
6. [nit] `src/harness/opencode/discovery.rs:265` and `src/harness/opencode/load.rs:11-12`: intra-doc links to the private modules `super::watch`/`super::follow`. From the public `Harness::load` doc this triggers `rustdoc::private_intra_doc_links`. Line 265 is also over 100 columns, because rustfmt does not rewrap comments. Change: write the module names in plain backticks without link syntax, and rewrap line 265.
7. [nit] `tests/opencode_live.rs:402-424` (`ten_quick_writes_are_coalesced`): the ten rewrites run back-to-back in a tight loop, so even an un-debounced worker would probably produce fewer than ten batches. The assertion is weak evidence of the debounce. Change: space the writes about 50 ms apart (below `DEBOUNCE`, total under `MAX_WAIT`) and assert at most 2 `Updated` batches.
