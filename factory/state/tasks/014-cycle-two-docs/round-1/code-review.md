1. [must-fix] `doc/SPEC.md:843` (§9.5), and `doc/SPEC.md:152` (§3.1), which points to it. The new sentence "Every field that is read is optional, and a field of an unexpected JSON type counts as missing instead of failing its line" is false, and §9.5 is a base rule that binds every later task and review. `src/harness/claude/wire.rs:3-8` says the opposite: "A known field with a different JSON type (other than `null`) still fails the line". So does the cycle's own spec, `factory/state/SPEC.md:137`: "a known field of the wrong JSON type fails the whole line". I confirmed this with a probe of `read_entry` in a scratch copy: a wrong-typed `uuid`, `timestamp`, `cwd`, `durationMs`, `isMeta`, `message.id` and `message.model` each fail the line. On OpenCode, `AssistantData.time`, `cost`, `model` and `content` (`src/harness/opencode/assemble.rs`) are strict too. The leniency covers the fields this cycle added, not every field that is read. Change: replace the sentence with what is built, along these lines: "Every field is optional and unknown fields are ignored. A known field of another JSON type fails its line, which is then skipped and counted, except where the field is read leniently and counts as missing: Claude `message.usage`, `message.stop_reason`, both `isApiErrorMessage` fields and `toolUseResult`; OpenCode `tokens`, `finish` and `error`; and every field the details overlay re-reads (§4.3)." In `doc/SPEC.md:152`, make "these fields" explicitly the detail fields of the bullet above, so that it does not read as a claim about every field in §3.1.

2. [must-fix] `docs/performance.md:88-95` and `:97`. The unfold bullet is wrong about the cause and the conclusion. It says unfolding takes 116 to 173 ms because the output is "1.5 MB, in a line of about 3 MB that has to be read and parsed again", that "the figure comes from the fixture and not from the application", and that this is "more than a frame". Timing every large output in a scratch copy of `tests/budgets.rs` shows otherwise:
   - In one run, 46 of the 47 outputs measured (the 48th is the scenario's, which is already unfolded and skipped) took 0.2 to 7.2 ms, among them larger ones (2 033 269 bytes: 0.3 ms; 1 959 957 bytes: 7.2 ms). In a busier run the slowest of these took 10.9 ms.
   - Only one takes about 115 ms (Shell, 1 573 956 bytes, 21 865 lines). It is in the same turn (`...06d3`) as the scenario's `large_section`, which `expand_large_output` has just expanded, because `tests/budgets.rs:312-318` runs the expansion before `worst_unfold`.
   - `Transcript::set_folded` invalidates the whole block (`src/components/transcript/nav.rs:255-266`), so unfolding that output lays out the expanded one again too. In one run with `worst_unfold` called both before and after the expansion, the worst unfold was 10.0 ms before and 115.1 ms after.

   So a plain unfold of a large output is still under the frame budget, as the page used to say. The old fixture's 8 ms suggests it had no second large output in that turn, though I did not measure the old fixture. The builder's "no regression" measurement still holds, but the page's explanation does not, and it would send the next reader to the wrong code. Change: keep the test as it is and correct the page, which leaves this a docs-only task. (Moving the `worst_unfold` call above `expand_large_output` in `tests/budgets.rs` is an acceptable alternative: it changes a reference line only, no budget, and the page then reports the plain figure.) Either way, state that a plain unfold takes up to about 10 ms and is under a frame, and that about 115 ms (116 to 173 ms over the builder's runs) is the cost of re-laying out a block that also holds an already expanded output of about 20 000 lines. Drop the "line of about 3 MB ... read and parsed again" cause and the "comes from the fixture and not from the application" sentence. At `:97`, change "This is the other interaction that takes more than a frame" to match, since expanding (and re-laying out an expanded block) is what exceeds a frame.
