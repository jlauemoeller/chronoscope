## Findings
1. [must-fix] `Prompt`, text longer than the prompt (it scrolls), cursor on a double-width character, 80x24 (and any width): the character under the cursor is not drawn. Only a blank cell with bg `cursor` shows in the last column. This happens at every cursor position in the right-pinned scroll region, not at one column only: `←`×1, ×2, ×5 and ×15 on a 63-character CJK query all show a blank cursor cell at col 74 instead of `本`/`日`/`語`. The cause: `visible_text` scrolls with `self.input.visual_scroll(width - 1)`. That keeps the cursor pinned to the last column with one cell reserved, and then `if shown + w > width { break; }` drops the two-cell character that does not fit. The result is a typed character missing from the prompt, which breaks the planner rule that the cell under the cursor is painted with bg `cursor` and the cursor stays visible. The same `Prompt` is reused for file paths later, where non-ASCII names are plausible. Change: when computing the scroll, reserve the display width of the character under the cursor (or 1 when the cursor is after the end), so that the whole character fits. That character must then be drawn with bg `cursor` over both of its cells, as already happens at ×40. Add a `Prompt` component test at width 30 with wide characters overflowing and the cursor on a wide character at the right edge (text + styled snapshot, or a cell assertion that the glyph is there with bg `cursor`). See `ui/prompt-wide-chars-cursor-inside-80x24.txt` (×1, ×2, ×5 and ×15 show the bug, ×40 is correct).
