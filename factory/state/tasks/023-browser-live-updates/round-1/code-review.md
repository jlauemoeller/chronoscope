## Findings
1. [nit] `src/components/transcript/mod.rs`, doc comment of `AppComponent::on` for `Transcript`. It still says the method returns `Msg::TranscriptChanged` when the view changed. Change: also say that it returns `Msg::NewSections(n)` instead when the key changed the new-section count (e.g. `G` / `End` resuming following).
2. [nit] `src/components/transcript/follow.rs`, `at_bottom`. The prepared window is reused when `w.size == size`, but its `offset` is not compared with `self.offset`. Every current path refreshes the window after moving the offset, so the result is correct today. A future path that sets `offset` without `refresh()` would get a stale answer, though. Change: filter on `w.size == size && w.offset == self.offset` so that a stale window falls back to the `covers` check.
3. [nit] `src/components/transcript/updates.rs`, `change_turns`. When the user is not following and an `Updated` batch shrinks the content enough that the end comes back into view (the offset is clamped in `refresh`), `following` stays false. The `↓ N new` indicator also stays until the next key or resize. This is rare, and the spec does not require it. Change (optional): when `counting`, call `self.update_following()` after `self.refresh()`, so that reaching the end this way also resumes following and resets the count. The App already re-reads the count after every forwarded update.
4. [nit] `src/components/transcript/updates.rs`, `reset` → `start_loading`. A `Reset` (the file shrank or was replaced) drops follow mode and returns the view to the top until `Loaded`, even if the user was following. This matches the build notes' reading that a reload is a fresh load, and the planner notes don't decide the case. Mention it to the Approver in case "stay at the end after a reload" is wanted.
5. [nit] `src/app/browser.rs` `sync_new_sections` and `src/app/selector.rs` `push_viewports`. The planner note says the `Transcript` "reports the count to the App as a `Msg` whenever it changes". The implementation sends `Msg::NewSections` only from keys. After forwarded `ModelUpdate`s and viewport changes, the App queries `NEW_SECTIONS_ATTR` instead, because tui-realm's `attr()` cannot return a `Msg`. The result is the same (AC 3 is met and tested), and the build notes record it, so this is acceptable. Change (optional): add a sentence to the `Msg::NewSections` doc in `src/app/mod.rs` saying that the App also reads the count back after updates it forwards, so the two paths are documented together.
6. [nit] `src/app/mod.rs`, the `Msg::NewSections(count)` arm of `update`. A key that changes the count returns `NewSections` *instead of* `TranscriptChanged`, even though the view moved too (`G` scrolls). The redraw then depends on `set_new_sections` → `refresh_status` → `set_attr`, which only runs when the count differs from the App's copy. The two counts are always in sync today, so nothing breaks. If they ever diverged, though, the scroll from `G` would not be redrawn. Change: in that arm, also call `self.request_redraw(RedrawRequest::Dirty)`.
