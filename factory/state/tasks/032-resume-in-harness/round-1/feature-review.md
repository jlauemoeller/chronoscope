## Summary
Resume in harness is implemented as the planner described. `R` in the browser and on a selected session row in the selector sends `Msg::RequestResume`. The `App` checks for a resume command, then for the cwd, then opens a `y/n` question in the help line. `y` stores a pure `ResumePlan` and quits. `run_app` then hands off through `hand_off(plan, &mut dyn Steps)`, which restores the terminal, changes directory, then runs the command (`exec` behind `#[cfg(unix)]`, `status()` elsewhere). Almost every acceptance criterion is covered by tests that would fail if the behaviour were wrong. One case of AC 2 is not met: with the Projects pane focused and a session still selected, `R` does nothing. I re-ran the gates: `cargo fmt --check` is clean, clippy with `-D warnings` is clean, and `INSTA_UPDATE=no cargo test` has 0 failures.

## Findings
1. [must-fix] With the Projects pane focused and a session still selected, `R` does nothing. In `src/components/project_list.rs`, `PaneKey::Resume => None` drops it, and `r_in_the_projects_list_does_nothing` pins that. The binding planner note makes the no-op depend on selection, not focus: "With no session selected (e.g. Projects focused with none selected) it does nothing." The qualifier "with none selected" would be pointless if focusing Projects alone disabled `R`. `R` is also bound as `selector.resume`, an action of the whole selector context, not of the Sessions pane. The selector keeps the session selection when Projects gets the focus (`focusing_projects_keeps_the_session_selection`). So in this state a session is selected, yet `R` does nothing, which matches neither branch of AC 2. Change:
   - In `ProjectList::on`, map `PaneKey::Resume` to a message the `App` resolves against its own selection. Either add a `SelectorMsg` variant, or have the `App` fill `Msg::RequestResume` from `selected_harness()` / `selected_session()`.
   - The `App` must still do nothing when no session is selected. Keep `r_with_no_session_selected_does_nothing`.
   - Update the component test `r_in_the_projects_list_does_nothing` to match.
   - Add an update test in `src/app/browser_tests/resume.rs`: focus Sessions with a session selected, focus Projects, press `R`, and assert the prompt `Resume <that id> in Claude? (y/n)` is shown. Then `y` must give that session's plan.
   - Update the decision in the build notes.
2. [nit] `src/app/browser_tests/resume.rs`, `a_long_missing_cwd_is_cut_at_its_start_so_the_toast_fits`: the width bound `<= 56` is a magic number. Change: derive it from `MAX_TOAST_WIDTH - TOAST_CHROME`, so the test stays correct if the toast width changes.
3. [nit] The wiring in `run_app` (`Some(plan) if result.is_ok()` → `SystemSteps` → `std::process::exit`) is not tested. The planner accepted this ("thin untested function"). The order of the steps is still checked through `hand_off`.
