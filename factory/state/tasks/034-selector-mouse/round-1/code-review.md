VERDICT: FAIL

## Summary
The routing design is sound. `hit_test` is a pure function over the `ScreenLayout` that `view` also uses, and the routing areas are refreshed from `update`/`resized`/`push_viewports`, never from `view`. The components map relative positions to rows and tabs correctly, and the tests are thorough and meaningful. The test gate passes. There is one real bug in the click path: in a Sessions list that was scrolled with the wheel while nothing was selected, a click makes the list jump under the pointer, so a double-click on that row selects a different session and does not open it.

## Findings
1. [must-fix] `src/app/mouse.rs`, `App::session_clicked` (`self.focus_pane(Pane::Sessions); self.session_selected(id.clone());`): the order of these two calls is wrong when the Sessions list has been scrolled with the wheel and nothing is selected, which is the state the "wheel only scrolls when nothing is selected" requirement creates. The list puts its cursor on the clicked row. Then `focus_pane` applies the §4.1 newest-session rule and pushes index 0, which resets the list offset to 0. Then `session_selected` pushes the clicked index, so the row is now drawn somewhere else. Verified with a scratch test at 80x22 (3 session rows, nothing selected). After two wheel steps down, line 0 shows s3. The first click selects s3, but the list jumps back to s1..s3 and s3 is now on line 2. The second press at the same spot, 100 ms later, selects s1, and `take_queued()` is empty, so the double-click does not open the session. Change: in `session_clicked`, call `self.session_selected(id.clone())` before `self.focus_pane(Pane::Sessions)` (or set `self.selector.session` before focusing), so the newest-session rule does not fire for a click on a row. The search and filtered paths are unaffected, because `session_selected` returns early there and `focus_pane` is a no-op. Add an update test to `src/app/mouse_tests.rs`: at `Msg::Resized(80, 22)`, wheel Sessions down twice with nothing selected, then click line 0. Assert that s3 is selected and still drawn on line 0 (or that the list offset is unchanged), and that a second press on line 0 within 400 ms queues `Msg::OpenSession(CLAUDE, "s3")`.
2. [nit] `src/components/project_list.rs` `on_mouse` / `src/app/mouse.rs` `takes_mouse`: in the filtered selector (`show_filtered`), the wheel over Projects still sends `ProjectSelected`. That changes the Projects selection and the Working Directory box while the filter stays on, although the `show_filtered` doc comment (task 033) says "The Projects pane is as at a start without the prefix". A click on Projects, by contrast, ends the filter. Consider ignoring the wheel over Projects while `selector.filtered.is_some()` (or ending the filter, as the click does), and cover the chosen behaviour with a test.
3. [nit] `src/app/mod.rs`, end of `App::update`: `refresh_routing()` runs after every message, including `Msg::Tick` (every 250 ms). It also runs twice per mouse event, because `mouse()` calls `update` again. That is cheap and correct, but it does more than the doc comment on `refresh_routing` says ("called when the screen, an overlay, the size or the toast changes"). Either update the comment or limit the call to the messages that can change the layout input.
4. [nit] `src/app/mouse.rs`, `MouseState::press`: only row presses update `last_press`. Row A, then a click on a tab or on empty pane space, then row A within 400 ms still counts as a double-click. Consider clearing `last_press` on any left press that is not a row press, for example in `App::mouse` before dispatch.
5. [nit] `src/components/list_pane.rs`, `ListCursor::set` doc comment ("a list nothing is selected in cannot have been scrolled"): this is no longer true now that `ListCursor::scroll` exists. The behaviour is fine. Rows are only pushed again on index snapshots and project or harness changes, never on `Tick` or activity and stats updates, and going back to the top there matches §4.1, which keeps the cursor on the newest session while nothing is selected. Change: reword the comment to say that a new row list resets a wheel scroll made with nothing selected.
