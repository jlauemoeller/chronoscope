VERDICT: FAIL

## Summary
The markdown renderer is well structured: parsing, layout, prose wrapping, char wrapping, highlighting, tables and the widget each have their own module. The tests are thorough, and the test gate passes. Two behaviours are wrong, though. Quote bars, table separators, rules and code-block spans do not derive from the `base` style, which breaks the binding planner note. And a tab in prose disappears on screen, so the words on either side run together. There are also a few small nits.

## Test gate
- cargo fmt --check: pass
- cargo clippy --all-targets -- -D warnings: pass
- cargo test: pass (717 lib tests passed, 1 ignored; all other suites pass; no `.snap.new` files)

## Findings
1. [must-fix] `src/markdown/mod.rs` `Styles::new` (`muted: Style::new().fg(...)`) and `src/markdown/layout.rs` `code_lines`: not every element style is derived from `base`, which the binding planner note requires ("Every element style is derived from it by adding modifiers or token colours"). The quote bar, table separators, header rule and horizontal rule start from `Style::new()`, and so do all fenced-code spans, which come straight from `theme.style(Token::Syntax*)`. Any modifiers on `base` are therefore dropped for these elements. This was confirmed with a probe: with `base = theme.style(Token::Thinking).add_modifier(Modifier::DIM)`, the `│ ` bar, ` │ `, `──┼──`, the rule and every code span (`fn`, `x`, `1`, …) had no DIM. Inline code does it correctly (`style.patch(self.styles.command)`), so the module is inconsistent. This matters for §8.2: the transcript styles selected and unselected sections through `base`, and code blocks and bars would escape that styling. Change:
   - Build `muted` as `base.fg(theme.role(Role::MutedForeground))`, or `base.patch(...)`.
   - In `code_lines`, map each highlighted span to `styles.base.patch(span.style)`. Leave the standalone `highlight_code` API base-free.
   - Extend `the_base_style_is_the_starting_point_of_every_element` (or add a test) so it renders a quote, a table, a rule and a ```` ```rust ```` block with a base that carries a modifier. It should assert that every non-blank span keeps the modifier.
   - The `every_colour_comes_from_the_theme` test can stay as it is.
2. [must-fix] `src/markdown/prose.rs` `words`/`is_gap`: a tab in prose is copied into the line as a literal `\t`. Ratatui's `Buffer::set_stringn` drops control characters, so `Text with tab\there` is drawn as `Text with tabhere`, and the words run together. This was confirmed through the `Markdown` widget into a `Buffer`. User prompts are rendered as markdown, and pasted text often contains tabs. Change: in prose, replace `\t` with spaces when building words or gaps, as `char_wrap` and `highlight_code` already do. For example, push `" "` (or the 4-space `TAB`) for a tab gap, so both the measured width and the drawn output are correct. Do the same for table cells and inline code, which reuse `Inline`. Add a test that renders through the widget/`buffer_to_text` (or asserts the line text) and checks the words stay separated.
3. [nit] `src/markdown/layout.rs:20` `layout(.., tight: bool)`: every caller passes `false` (`mod.rs:79`, `layout.rs:108`), so the parameter and its branch are dead. Remove the parameter and update the doc comment.
4. [nit] `src/markdown/layout.rs` `list_lines`: an empty list item (`- a\n-\n- c`, or `- \n- b`) is drawn as a blank line with no `• `, so the item vanishes. When `item_lines` returns nothing, push `Line::from(marker)` (trimmed if you prefer) instead of `Line::default()`. Add a small test.
5. [nit] `src/markdown/widget.rs` `Markdown::render`: if `area` reaches past `buf.area`, `buf.set_line` panics with "index outside of buffer". A probe with a 10x5 area on a 10x2 buffer showed this. Strictly that is a caller error, but ratatui's own widgets guard against it. Start `render` with `let area = area.intersection(buf.area);`. A virtualised transcript that draws partly visible blocks makes this worth having.
6. [nit] `char_wrap(text, 0, style)` wraps at 1 cell (`width.max(1)`), while `render_markdown(src, 0, ..)` returns no lines. Pick one behaviour for width 0 and document it in the `char_wrap` doc comment.
7. [nit] `src/markdown/highlight.rs`: the `LOADS` counter and its `fetch_add` exist only for a test, but they run in production builds too. Consider gating the counter with `#[cfg(test)]`. Separately, the `comment` rule is kept apart from `RULES` (`COMMENT` chained in `rules()`) for no clear reason; fold it into `RULES` as a tenth entry.
8. [nit] `src/markdown/layout.rs` `item_lines`: a nested list sits 2 cells in under any marker. This follows the planner note literally, but under an ordered marker it starts inside the marker column (`1. one` / `  • inner`). This is acceptable per the spec. Mention it to the transcript task, in case aligning nested lists under the item text reads better.
