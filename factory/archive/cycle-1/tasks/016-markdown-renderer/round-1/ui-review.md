## Findings
1. [nit] `Markdown` widget, sample document, widths 4 and 8 — when the width is smaller than the prefix + 1, content is clipped without any sign. At width 4 the nested bullet items ("Nested bullet one/two") need 2 (nest) + 2 (marker) + 1 cells, so their text is drawn past the area and about 50 rows come out blank (`ui/sample-4-nested-list-hidden.txt`). At width 8 the table's three 1-cell columns plus separators need 9 cells, so the third column (`Status`) is clipped off entirely (`ui/sample-8-table-last-column-clipped.txt`). The build notes disclose this, and these widths are not realistic inside a transcript block. Change (optional): when the nest/marker prefix would leave less than 1 cell, shrink or drop it so at least one cell of text stays visible. For a table that cannot fit even at 1 cell per column, drop the trailing columns or fall back to an unseparated layout instead of letting the buffer clip them.
2. [nit] `Markdown` widget, any element with an indent or chrome, when `base` has a background or modifiers, @ 20 — the base background covers only text spans. Code indents, list hang/nest indents and table cell padding are `Span::raw`. The quote bar, table separators/rule and horizontal rule use `Style::new().fg(muted_foreground)`, and code spans use the bare `syntax.*` style. A base with a background therefore shows gaps (`ui/base-with-background-20.txt`, rendered with a hand-built `thinking` fg + `primary` bg base). Nobody can hit this today. `Theme::style` gives text tokens only a foreground: `theme/parse.rs` accepts `bg` only for `search_match`/`toast`, and `without_colors` adds modifiers only to `search_match`. For every reachable base, `Style::new().fg(muted)` therefore renders the same as `base.fg(muted)`, and the planner rule "every element style is derived from `base` by adding modifiers or token colours" holds in output. Change (optional, cheap insurance for later transcript tasks that may pass a richer base): build `Styles::muted` as `base.fg(muted_foreground)`, style indent and padding spans with `base`, and patch syntax token styles onto `base` (`base.patch(theme.style(SyntaxX))`).
3. [nit] `code_block_only_at_60_columns_styled` and `sample_document_at_80_columns_styled` (default theme) — in `default`, `syntax.keyword`/`syntax.type` share `accent`, `syntax.string`/`syntax.number` share `warning`, and `command` equals `foreground`. So the styled snapshots alone cannot tell keyword from type, string from number, or inline code from prose. The unit tests with a distinct-colour theme (`rust_tokens_use_the_syntax_tokens`) cover the mapping, so this is only a reviewability point. Change (optional): add a styled code-only snapshot with a theme whose `syntax.*` tokens are all distinct.
