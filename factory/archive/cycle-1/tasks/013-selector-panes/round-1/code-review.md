## Summary
The selector panes, the Port → `UserEvent` → `GlobalEvents` → `Msg` path, keeping the selection by id, activity flags, layout and snapshots are well structured and match the spec. The tests are thorough. The test gate is green, and the re-accepted pre-existing snapshots differ only by the new tabs, panes and Working Directory box. One real bug blocks the round: moving the selection inside the Sessions list never asks for a redraw, so `j`/`k`/`↑`/`↓` in Sessions do not show on screen until something else marks the frame dirty.

## Findings
1. [must-fix] `src/app/selector.rs:303-307` (`App::session_selected`): when the user moves in the Sessions pane, `SessionList` changes its own cursor and sends `SelectorMsg::SessionSelected`. The handler only updates `self.selector.session` and never calls `request_redraw`. `run_loop` (`src/app/runtime.rs`) draws only when `take_redraw()` returns something other than `None`. `Tick` does not request a redraw unless the active flags change, so the moved `>`/band stays off screen until an unrelated event marks the frame dirty: a stats or snapshot event, a focus change, or a resize. Moving in Projects works only because `project_selected` pushes attributes through `set_attr`, which does request a redraw. Change:
   - in `session_selected`, after `self.selector.session = Some(id);`, call `self.request_redraw(RedrawRequest::Dirty)` (only when the id is known and differs from the current one);
   - add an update test in `src/app/selector_tests.rs`: focus Sessions, call `app.take_redraw()`, press `j`, and assert `app.take_redraw() == RedrawRequest::Dirty`. This is the test that would have caught the bug; `keys_drive_the_selection_through_the_focused_component` checks only domain state.
2. [nit] `src/components/global_events.rs:53-56`: the index-event subscription uses `subscription_clause()`, the same clause as the global keys. It is `SubClause::Always` today. §1.4 says a later task narrows that clause so global keys do not fire while `Prompt`, `HelpOverlay` or `ThemeSelector` has focus. Once it does, worker events would be dropped while an overlay is open, and stats events are not re-sent. Give the index subscription its own `SubClause::Always`, with a comment saying worker events must never be filtered by focus.
3. [nit] `src/app/selector.rs:229`: `keep_selection` clones the whole project list (`self.selector.projects().to_vec()`) only to get around the borrow. Clone the `Arc<Vec<Project>>` of the current `HarnessData` instead, e.g. `self.selector.current_data().map(|d| Arc::clone(&d.projects))`.
4. [nit] `src/harness/mod.rs:115-123`: `registered_harnesses` repeats the enablement logic of `build_harnesses_with_home`, and only the `registered_harnesses_match_the_constructed_ones` test keeps the two in sync. Consider deriving the ids from one shared source, such as a list of `(HarnessId, enabled)` pairs, so adding OpenCode later cannot update one and miss the other.
5. [nit] `src/app/index_port.rs:61-72`: `index_event_kind()` builds a dummy `Snapshot` (two empty `Arc`s) just to subscribe by discriminant. It works, but its doc comment should say that `EventClause::Discriminant` compares only the `UserEvent` variant, so the payload is irrelevant. Otherwise a reader may think snapshots of Claude are being filtered.
6. [nit] `src/app/selector.rs:69` (`SelectorState::stats`): the stats map is keyed by `(HarnessId, SessionId)` and never pruned when sessions disappear from a snapshot. It is small in practice. Consider dropping the entries of sessions that are absent from the latest snapshot of their harness.
7. [nit] `src/app/selector.rs:211-215` and the `the_first_available_harness_by_number_is_shown` test: the initial harness is the one whose available snapshot arrives first. The test asserts that OpenCode stays selected when its snapshot comes before Claude's. Today's worker builds harnesses in tab order (`src/index/worker.rs:277-280`) and only Claude is registered, so users cannot see this. Still, "first available registered harness by number" would be stated more robustly by re-picking while the user has not yet moved, or the test should note that it relies on that ordering.
8. [nit] `src/components/harness_tabs.rs`: §8.2 says the selected tab is "`primary`, underlined". The build draws the `━` row in `primary`, as the planner note says, but does not add `Modifier::UNDERLINED`. This is defensible and documented in the build notes. It is listed only so the Approver knows it was a deliberate choice.
