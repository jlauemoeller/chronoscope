## Findings
1. [nit] `src/index/worker.rs:165-168`, the doc on `Coordinator::seq`. It says "A result is only sent when its `seq` is newer than the last one sent for its session". That is true only for outdated-key results: a result for a current key is sent unconditionally, as `record`'s doc correctly states. Change: reword it to "An outdated result is only sent when its `seq` is newer than the last one sent for its session, so an older result never overwrites a newer one."
2. [nit] `src/index/worker.rs:246-249`, `pool_thread`'s `catch_unwind`. A caught panic still runs the global panic hook. Today that hook prints `thread 'index-stats-N' panicked at ...` to stderr, which would land inside the TUI's alternate screen. Later, the terminal-restoring hook required by SPEC §9.5 would fire on a worker-thread panic while the app keeps running. No hook exists yet, so this is not in scope here. Change: add a short comment at the `catch_unwind` noting that the §9.5 panic hook must tolerate caught panics on `index-stats-*` threads (for example, restore the terminal only for panics that are not caught). Alternatively, carry this as a note for the task that installs the hook.
3. [nit] `tests/index_stub.rs:286-298`, `a_stale_result_after_newer_stats_were_sent_is_dropped`. The 500 ms quiet window also passes if the held version-1 `Done` never reaches `record` within the window, so the drop is not positively observed. Change: after the window, set `stub.version` to 3 and assert that the next `Stats` has `turns == 3`. The version-3 job is deferred until version 1's `Done` clears `pending`, so receiving it proves that the version-1 result was recorded. Because a turns-1 event would arrive first, it also proves that the result was dropped rather than sent.
