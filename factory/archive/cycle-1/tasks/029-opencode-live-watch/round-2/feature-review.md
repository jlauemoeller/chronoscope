## Findings
1. [nit] `src/harness/opencode/watch.rs` `MAX_WAIT` (a 1 s cap counted from the first event) is still a deliberate departure from the planner note's pure trailing debounce. It is documented in the module doc, and no AC depends on it. I'm carrying it forward so the Approver sees it. No change needed.
2. [nit] `tests/opencode_live.rs` `the_index_keeps_following_after_the_wal_is_deleted_and_created_again` waits a fixed 600 ms for the rebuild that the WAL deletion triggers. On a very slow machine, that rebuild could start after the new insert. The test could then pass without a working watch on the new WAL (a false pass, not a flaky failure). Optional change: after deleting the WAL, wait for the `Snapshot` or `Stats` events that follow the deletion, then drain, instead of sleeping a fixed time.
3. [nit] `src/harness/mod.rs` `watch_files` says it returns a subset of `watch_paths`, but nothing checks this. In `src/index/worker.rs` `watch`, a file that is in `watch_files` but not in `watch_paths` would still be watched. Optional: add a `debug_assert!` in `watch` that every entry of `files` is in `paths`.
4. [nit] The known limits are now documented in the `follow.rs` module doc, and none of them is required by an AC: deleted rows give no `Reset`, a new part of a row updated in place is added at the end of its turn, a row unparsable when first read is never re-shown, injected entries that straddle passes stay in the earlier turn, and a same-length rewrite within the same millisecond is missed. Listed for the Approver; no change needed.
