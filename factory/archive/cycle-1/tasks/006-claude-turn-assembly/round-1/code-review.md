VERDICT: FAIL

## Summary
The model types, tool mapping, lazy outputs, incremental API and tests are well built. The test gate passes, and a scratch probe over all 543 local Claude transcripts (outside the repo) found no panics, no lazy `text()` errors, no dropped tool calls and no wrongly pending calls. One real data-loss bug remains. Transcripts without `apiBlockIndex` lose content blocks: every one-block line of a message gets the id `<message.id>:0`, so later blocks of a different kind overwrite earlier ones. This happens in real Claude Code 2.1.252 sessions on this machine.

## Findings
1. [must-fix] `src/harness/claude/assemble.rs:363-365` (with `upsert` at `:504`) — when an `assistant` line has no `apiBlockIndex`, the block index is the position inside that line's `content` array. Older transcripts have one block per line, so this is always `0`. Every text and thinking block of a message then gets the id `<message.id>:0`, and `upsert` replaces whatever item already has that id, regardless of kind.
   - Repro: four lines sharing `message.id` `m` with no `apiBlockIndex`, in the order thinking, text "first", `tool_use`, text "second". They assemble to one Text ("second") plus the call. The thinking block and "first" are lost.
   - Real data: `~/.claude/projects/-home-jacob-Development-projects-focus/40f5827e-….jsonl` (`version` 2.1.252) has no `apiBlockIndex` on any of its 242 assistant lines. It has 95 thinking blocks, but only 34 Thinking items survive assembly. Because text lines follow thinking lines, the text overwrites the thinking.
   - This breaks SPEC §5.1 rule 3 ("merged into one message, keeping their content blocks in order") and the AC "distinct blocks are not merged". It loses data silently.
   - Required behaviour: without `apiBlockIndex`, distinct blocks of a message must never collide. Only a real re-send of the same block may replace an earlier one. For example, keep a per-message running block counter across lines, or replace only when the block at that index has the same kind and the new text extends the old one. Choose whatever is consistent with real older transcripts.
   - Tests: replace `tests/claude_assembly.rs:250` `without_api_block_index_the_position_in_the_line_is_the_index`, which currently locks in the colliding behaviour. Add a fixture or inline test with separate thinking, text, `tool_use` and text lines that share a `message.id` and have no `apiBlockIndex`. Assert that all four items survive, in order, with distinct stable ids. Also cover chunked and line-by-line equivalence for that case.
2. [nit] `src/harness/claude/assemble.rs:310-321` — if a turn's first message is `<synthetic>` or has no model, the turn's `model` is set to that value. The next real message then emits a `ModelChange`. One local session starts a turn with a synthetic message. Change: set the turn's model, and the initial `last_model`, from the first *real* model seen in the turn, and fill `turn.model` in when it arrives.
3. [nit] `src/harness/claude/wire.rs:3-4` — the module doc says format drift "degrades to missing data rather than a failed line". That is not true for known fields with the wrong type. For example, `"isMeta": null` against `bool` fails the whole `Entry`, and one badly typed field in any `Block` sends the whole `content` to `Content::Other`. Real data showed no such case. Change: either correct the doc comment or deserialize these fields tolerantly (e.g. `Option<bool>`, or a lenient deserializer per block).
4. [nit] `src/model/output.rs:62` — the harness-agnostic `model` module calls `crate::harness::claude::extract_result_text` through `LineFormat::Claude`, so `model` depends on an adapter. Each new harness would have to edit `model`. Change (later, at the latest with the OpenCode adapter): let `OutputSource` carry an injected extractor (e.g. `Arc<dyn Fn(&[u8], &str) -> Option<String> + Send + Sync>` or a trait object), so that `model` does not name harnesses.
5. [nit] `src/harness/claude/mod.rs:8` and `src/model/output.rs:132` — `extract_result_text` is re-exported as public API, and `count_lines` is `pub` inside a private module, but both are only used inside the crate. Change: make them `pub(crate)`.
6. [nit] `src/harness/claude/assemble.rs:134` — `push_chunk` rescans the whole buffered partial line for `\n` on every chunk. A long line split over many chunks is therefore scanned quadratically. Lines on this machine reach about 1 MB, so this is harmless today. Change: start the newline search at the previous buffer length.
7. [nit] `src/harness/claude/assemble.rs` (`push_line` vs `push_chunk`) — mixing the two desyncs `pending_start`, because `push_line` does not advance it. Change: document that each assembler uses one of the two, or advance the offset in `push_line` too.
8. [nit] `src/harness/claude/assemble.rs:350-360` — the hand-written all-`None` `Block` literal could be `Block { kind: Some("text".into()), text: Some(text), ..Default::default() }` with `#[derive(Default)]` on `Block`.
9. [nit] (for task 036) `Arc::make_mut` on a turn the UI already holds deep-clones the whole turn on every later update to it. A very long Assistant turn that is streamed in chunks therefore costs O(turn size) per update. This follows from the planner's `Arc<Turn>` design and is not a defect here, but it should be measured against the §9.2 budgets.
