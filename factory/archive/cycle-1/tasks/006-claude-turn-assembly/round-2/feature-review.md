## Findings
1. [nit] `src/harness/claude/assemble.rs` `block_id`: without `apiBlockIndex`, re-sends are detected only against the message's *single most recent* block. A cumulative re-send of a multi-block line would therefore duplicate every block, e.g. `[thinking T, text A]` followed by `[thinking T, text A, tool_use]`: on the second line, T is compared against A, gets a new id, and so on. The round-1 position-in-line scheme handled this case. No local transcript has a multi-block line without `apiBlockIndex`, so this is theoretical. Change (optional): when a line without `apiBlockIndex` carries several blocks, first try to match block `i` against the message's block `i` (same kind plus prefix/signature), and only then fall back to the running counter. Add a test with a cumulative two-line re-send.
2. [nit] Same function: two distinct consecutive text blocks of one message, where the second starts with the first (or the two are identical, e.g. "OK" then "OK"), merge into one. This does not occur in local data. Change (optional): document the limitation in the `block_id` doc comment.
3. [nit] Round-1 feature-review findings 3 (origin-less current-format `user` entries become User turns) and 4 (no scrubbed real-excerpt fixture) are still open, deliberately, because the Builder cannot edit task files. Change: the orchestrator or planner should add them to task 007's (or 009's) scope.
4. [nit] `turn_starting_with_a_synthetic_message_takes_the_first_real_model_without_a_note` checks only the final turns. The fix changes `turn.model` on an already-appended turn and sets `changed`, which is correct, but no test checks that this emits `Updated`. The replay tests use the fixture, which has no turn that starts with a synthetic message. Change (optional): in that test, also feed the lines one by one, apply the emitted updates, and assert that the replayed turns equal the final turns.
