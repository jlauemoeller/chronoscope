## Findings
1. [must-fix] Consecutive injected entries are not collapsed when a batch flush puts them into a User turn that has no reply yet. In `src/harness/claude/assemble.rs` `flush_current` (the `else if` branch, around line 504), `turn.items.push(item)` always appends a new `Injected` item. The Assistant branch just above merges into a trailing `Item::Injected` instead. I reproduced it against the crate with a scratch probe. Batch 1 is `prompt, hook A`, followed by `flush_held()`; batch 2 is `hook B, reply`, followed by `flush_held()`. The User turn ends up with two items, `[Injected(1), Injected(1)]`. Parsing the same bytes as a whole gives `[Injected(2)]`. This is the common live case: the prompt and its hook/IDE attachments are written before the first reply arrives, and task 022 flushes at the end of every batch. It breaks SPEC §5.6 ("Consecutive injected entries collapse into one section"). Change: in the User-turn branch, merge the flushed entries into the last item when that item is an `Item::Injected` added by an earlier flush after the prompt, as the Assistant branch does. Do not merge into the pre-prompt item that `start_user_turn` puts first, because the prompt separates those entries. For example, keep a `user_flushed_after_prompt: bool` that `start_user_turn` resets. Add a test that feeds `prompt, A`, calls `flush_held()`, feeds `B, reply` and calls `flush_held()` again. It should assert that `asm.turns()` equals a whole-file parse of the same bytes (one `Injected` item with two entries, same id), and that replaying the returned updates gives the same turns.
2. [nit] Entries held after a trailing Compaction turn, or with no turn at all, are dropped from `into_turns()` / `finish()` output. Probe: `prompt, reply, compact_boundary, hook A`, then `finish`, gives no item for A. The planner notes allow this ("If there is no turn yet, they go into the next one"), and `entries_with_no_turn_to_hold_them_are_not_invented_into_one` pins the no-turn case. Consider logging at debug when `into_turns()` discards held entries, so it is visible.
3. [nit] `flush_current` also merges across `turn_duration` and tool-result entries (test `trailing_entries_collapse_into_the_previous_injected_item_of_the_turn`). The planner notes say "with only noise between them", and `turn_duration` is not in the noise list. This is visually reasonable (neither produces an item) and the build notes document it, but the doc comment at `assemble.rs` around line 491 could say explicitly that this deliberately extends the planner rule.
4. [nit] `check_blocks` runs on every `assistant` line, so a re-sent message (older transcripts without `apiBlockIndex` repeat a message with grown content) that contains an unknown block is counted once per re-send. That inflates the "N entries could not be parsed" note. Consider counting unknown blocks once per `(message id, block position)`.
5. [nit] The fixtures are hand-written rather than "trimmed real sessions, scrubbed" (SPEC §9.6, planner notes "scrubbed, as in task 006"). This matches the precedent task 006 set and is documented in `tests/fixtures/README.md`, so no change is needed now. The README could mention the version (2.1.x) of the real compaction sample that `compaction.jsonl` was modelled on.
