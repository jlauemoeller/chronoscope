VERDICT: FAIL

## Summary
The virtualised `Transcript` is well built. It has a lazy prefix-sum layout cache with binary-search lookup, a pure `view` over a prepared window, clipped first and last blocks, updates keyed by `SectionId`, and thorough tests, proptests and all seven snapshots. The gate is green, and the snapshots stay deterministic under `TZ=Pacific/Kiritimati`. One behaviour bug blocks a PASS. When the selected section is taller than the viewport and has been scrolled out of view, `Cmd::Move` pages the viewport blindly. It neither brings the selection into view nor moves to the next section.

## Findings
1. [must-fix] `Cmd::Move` with a tall selected section that is off screen scrolls one page and nothing else. In `src/components/transcript/nav.rs`, `page_through` only checks whether the section extends past the viewport edge in the step's direction. It never checks that the section is visible. Reproduced in a scratch copy:
   - Set a 60x10 viewport over 8 short replies, then an unfolded 40-row user prompt `u`, then one reply.
   - `select(u)`, then `scroll_to(0)`, then one `Cmd::Move(Down)`.
   - The offset goes 0 → 10. `u` stays selected. The frame shows blocks "Before 3"/"Before 4" with no `▒` rows.

   Each further `j` blindly pages again. The Up branch has the same flaw: with offset 500 and the section at rows 100..150, it pages to 490. A short off-screen selection behaves differently: the next section is selected and revealed. So this breaks the planner's "`Cmd::Move` … scrolls it into view" and SPEC §6.3 "Selecting a section scrolls it into view". The page-through rule only applies to a section the user is looking at.

   Change: in `page_through`, return `None` unless `section` overlaps `offset..offset + height`, so that Move falls through to the neighbour step. That step selects the next/previous section and reveals it with `reveal`. Revealing the current selection first would also be acceptable; pick one and document it. Add a test in `tests.rs`: a tall selected section scrolled fully out of view with `scroll_to`, then one `Cmd::Move` in each direction. Assert that the selected section's rows lie within the viewport afterwards.
2. [nit] `truncate_output_lines` is stored and queryable but has no effect, because no 017 renderer reads it. This is acknowledged in the build notes. Meanwhile `set_truncate_output_lines` (`mod.rs`) calls `invalidate_all`, which re-measures every block for nothing. Change: drop the invalidation until a renderer reads the value, or add a `// TODO(task NNN)` naming the task that will wire it in.
3. [nit] `restore_selection` (`updates.rs`) always calls `self.sections_of(at)`, so it runs a full layout of the selected block on every `Appended` batch, even when that turn was not touched. That is per-batch work during streaming load (§9.2). Change: return early when `before` is `None`, the selected turn was untouched and `show_system` did not change.
4. [nit] `cursor()`, `cursor_in` and `neighbour` (`nav.rs`) run a full `TurnBlock::layout` of the selected block, and sometimes the neighbours' too, on every `Move`/`Submit`. For a huge unfolded tool output this is costly per keypress. Change: consider reusing `Window::blocks[..].layout.section_rows()` when the block is in the prepared window.
5. [nit] `clipped_blocks_equal_the_slice_of_the_full_rendering`, and the frame check in the proptest (which also uses `trim_end`), compare text only. A clipping regression that only affects styles would pass. Change: also compare one styled slice, for example with `buffer_to_styled` on a clipped first block.
6. [nit] In `tests/cache_lookup.rs`, `locate_is_a_binary_search_over_known_prefix_sums` has a dead variable: `start` is assigned but never used. Change: remove it.
7. [nit] `updated_replaces_a_turn_in_place_keeping_selection_and_folds` does not directly assert the turn's position. Change: add `assert_eq!(t.turn(1).unwrap().id(), &TurnId::from("t2"))` after the update.
8. [nit] An unprepared `view` (an area size that was never announced) clones the whole `LayoutCache` on every frame. This is documented and correct, but worth a `debug_assert`-style log or comment noting that the App must send `VIEWPORT_ATTR` on resize to stay within the 16 ms budget.
